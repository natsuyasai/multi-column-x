Rust 層（src-tauri/）

Multi Column X のバックエンド。設定の永続化、X を表示する WebView の生成と管理、アカウントのログイン検出、 アプリ更新・動画保存・バックアップなど「OS に近い仕事」を担います。このページでは責務と公開 IF（外部設計）、 各モジュールの役割・設計判断・落とし穴（詳細設計）を説明します。

前提知識

Rust や Tauri を触ったことがなくても読めるよう、このプロジェクトを読むのに最低限必要な概念だけ挙げます。

概念 このプロジェクトでの意味
Tauri v2 メインウィンドウは React、バックエンドは Rust。両者は invoke と イベント でやり取りする。
コマンド #[tauri::command] を付けた Rust 関数。lib.rs の generate_handler! に登録すると JS から呼べる。引数は serde で JSON から復元される。
State .manage(AppState::new()) で登録する共有オブジェクト。複数コマンドから app.state::<AppState>() で参照する（内部は Mutex）。
capability（ACL） アプリ独自コマンドは build.rs の AppManifest に列挙し、capability で allow-<コマンド名のケバブケース> を許可しないと呼べない。
条件コンパイル 同じコマンド名で #[cfg(desktop)] 版と #[cfg(mobile)] 版の 2 実装がある場合が多い。 変更時は必ず両方を確認する。
serde の命名 Tauri v2 は JS→Rust のケース変換をしない。JS が camelCase で送る項目は #[serde(rename = "…")]、コマンド引数なら #[allow(non_snake_case)] の引数名で受ける。
Result とエラー型 コマンドは Result<T, E> を返す。E は String（旧来）または種別コードだけを持つ AppError / BackupError。JS 側では Promise の reject になる。

外部設計

責務と境界

  • 設定（settings.json）の読み書き・破損復旧・バックアップ/リストア
  • カラム/ポップアップ/コンポーズの WebView 生成・配置・破棄、inject スクリプトの組み立てと注入

ACL（誰がどのコマンドを呼べるか）

x.com を表示するカラム/ポップアップ WebView には remote capability で IPC（window.__TAURI__）が注入されます。 外部コンテンツにアプリのコマンドを開放することになるため、二重に防御しています。

  1. ACL：build.rs の AppManifest（定義）→ capability（許可）。 default.json は main 専用、column-webview.json は x.com/twitter.com 系ドメイン限定で、 inject が使うコマンド（report_*・ポップアップ系・download_video）だけ。 desktop の更新用に updater.json もある。
  2. コード側：多くのコマンドが require_main_caller で caller の WebView ラベルが main であることを検査する。
コマンドの追加・削除は 3 点同時

lib.rs の generate_handler!、build.rs の AppManifest、 capabilities/*.json の allow-…。漏れると実行時に 'not allowed by ACL' で拒否されます。 acl_contract.rs が cargo test で検出します。

設定の永続化

設定は tauri-plugin-store が settings.json に持ちます。壊れても起動できるよう、 次の仕組みで守っています。

  • アトミック保存：save_store_atomically が一時ファイル → sync → rename で置換し、直前世代を settings.json.prev に残す。Store::save を直接呼ばない。並行保存 （save_settings と終了時の windowBounds 保存）は SAVE_LOCK で直列化。
  • 起動時復旧：setup の冒頭で recover_settings_file が JSON として読めるか検査し、 壊れていれば退避して .prev から復元。結果は SettingsRecoveryState に入り、 最初の load_settings が React に伝える。
  • 順序は崩さない：「復旧 → 自動保存を無効にしたストアの登録」。ストア生成後だとプラグインが読み込み失敗を握りつぶし、 自動保存が生きているとアトミック書き込みをすり抜ける。
  • 既定値の 3 点同期：Rust の impl Default（構造体レベル #[serde(default)] が唯一の定義）、 TS 側の既定値、contracts/default-settings.json。変更時は 3 箇所同時に更新（契約テストが一致を検査）。
  • バックアップ/リストア：出力は BackupGlobalSettings のホワイトリスト。 復元は apply_restore（退避 → 置換 → アトミック保存 1 回）。

desktop/mobile 差分：windowBounds の保存・復元は desktop のみ。バックアップのファイル選択は desktop が tauri-plugin-dialog、Android が Kotlin の SAF（JNI）。

詳細：settings-file-crash-safety-notes.md、 backup-restore-notes.md

WebView 管理

X の画面は WebView で表示します。種類は 3 つで、ラベル接頭辞で区別します （column- / popup- / compose-。ほかに add-account- と extension-）。

  • Windows / macOS：window.add_child() でメインウィンドウの子 WebViewとして配置。
  • Linux：子 WebView が使えないため、親付きの独立 WebviewWindow。親クリップが効かないので 横スクロール時のはみ出しを linux_column_layout で幅を縮めて制御し、WebProcess クラッシュを検知して column-webview-crashed を emit する（過去にデグレした領域。変更時は必ず参照ノートのテスト方針に従う）。
  • 子 WebView は OS ネイティブ要素なので CSS の z-index が効かない。ダイアログ表示中は x:-9999 へ退避する運用。
  • カラム/ポップアップは Kotlin 側のネイティブ Android WebView（content FrameLayout のオーバーレイ）を JNI （android_bridge.rs → MainActivity.kt）で生成/破棄/eval する。
  • ネイティブ WebView は Tauri IPC 非対応のため、ポップアップからの報告は専用ブリッジ経由 （例：report_official_settings_from_android）。
  • MainActivity.kt のメソッドシグネチャを変えたら proguard-rules.pro も同時更新 （リリースビルドだけ NoSuchMethodException になる）。

builder の必須設定

WebView builder を新設・変更したら次を必ず付けます（契約テストが検査）。

設定 理由
.on_new_window(external_link::new_window_handler(app.clone())) target=_blank / window.open を http/https/mailto/tel だけ既定ブラウザで開き、常に Deny （アプリ内に新規ウィンドウを作らない）。desktop の opener 自動クリックスクリプトは無効化している。
.disable_drag_drop_handler() Windows で Tauri 既定のファイルドロップ処理が X ページの HTML5 DnD を横取りするのを防ぐ。
#[cfg(windows)] .browser_extensions_enabled(true) アカウントの data_directory を使う全 builder に必須。同一ディレクトリの WebView2 環境はフラグが 食い違うと生成に失敗する（ERROR_INVALID_STATE）。
.initialization_script(…) inject スクリプトの注入。inject ページ参照。

close() と destroy()

常駐コンポーズは × を prevent_close() + hide() で握るため、close() では閉じません。 メインの CloseRequested（lib.rs）で compose- ウィンドウを明示的に destroy() しています。prevent_close を使う常駐ウィンドウを新設したら、同じ場所に destroy を必ず追加してください。

詳細：linux-webview-notes.md、 linux-column-spec.md、 external-link-new-window-notes.md、 compose-popup-topbar-notes.md

アカウントとログイン検出

アカウントごとに独立したデータディレクトリ（Cookie 等）を持ち、WebView の data_directory として使います。 ログイン完了の検出は IPC でも JS 注入でもなく、Rust 側で行います（ログイン画面の遷移を JS 注入に依存させないため）。

open_add_account_window が add-account-<uuid8> ウィンドウで https://x.com/login を開き、tokio タスクが URL を 500ms ごとにポーリング。パスが /home になったら twid Cookie から X ユーザー ID を読み、 account-login-complete を emit して終了（最大 10 分で打ち切り）。コマンド自体は即座に accountId / dataDirectory / windowLabel を返す。再認証は account-reauth-complete。

open_add_account_window が AddAccount Activity を JNI で起動し、コマンド自体がブロックして アプリデータ配下の add_account_login_complete センチネルファイルを 500ms ごとにポーリング （キャンセル用の add_account_login_cancelled もある、最大 10 分）。AddAccount.kt がファイルを書くと その内容から xUserId を取り出して戻り値で返す。メイン WebView の JS が止まっていても tokio は動き続ける。

  • delete_account_data は accounts 配下のパスのみ許可し、ファイルロックに備えて 200ms 間隔でリトライ。
  • 再認証（既存アカウントのログインし直し）は新セッションのディレクトリを返し、呼び出し側が対象アカウントへ Cookie を上書きする。 詳細は release-theme-reauth-notes.md。

エラー設計

  • Rust は文章を返さない。新しめのコマンドは AppError { code, detail? } （app_error.rs）を返す。code は <領域>.<camelCase>（例： extension.notFound）で、React が辞書 messages:rustError.* で翻訳する。 コードを追加したら src/locales/{ja,en}/messages.json にも足す（契約テストが検査）。
  • detail には OS/WebView 由来の生の文字列や HRESULT の 16 進など、文言に混ぜない情報だけを入れる。
  • 旧来のコマンドは Result<_, String>（英語固定の短い文字列）。バックアップは専用の BackupError。
  • ウィンドウタイトル等 Rust が直接使う文言は ui_language.rs の ui_text（ja/en の表）。 表示言語の解決規則は TS の language.ts と同じ。
  • 開発者向けログ・expect・panic のメッセージは英語固定 （log_language_contract.rs が日本語を検出して失敗にする）。

詳細：i18n-notes.md

その他の機能

自動更新

tauri-plugin-updater が tauri.conf.json の公開鍵（minisign）で署名検証してから適用。 再起動は tauri-plugin-process。capability は updater.json。

install_apk_update を 3 層で検証：呼び出し元 main 限定／URL は自リポジトリの GitHub Releases の .apk のみ（.. や ? 等を拒否）／Kotlin 側で SHA-256 照合（fail-closed）。

動画ダウンロード

desktop は download_video。mp4 progressive があれば 1 ファイル、HLS のみなら映像・音声を別ファイルで保存。 URL は video.twimg.com 系のみ許可（SSRF 対策）、検証を経る公開 API と実 I/O を分離。進捗は video-download-progress。Android はネイティブ通知付きの別経路（handle_android_video_download_request）。

Linux コーデック / OpenH264

AppImage は H.264/AAC のデコーダが不足しがち。check_media_codec_support で判定し、 download_and_enable_h264（Linux desktop・x86_64 のみ）が Cisco OpenH264 を取得 → SHA-256 検証 → 展開 → openh264_lib_dir() へ配置する。linux_codec_env は起動時に LD_LIBRARY_PATH を整えるため、変更が必要なら自プロセスを再起動する（動的リンカが解釈するのは起動時一度きりのため）。 Linux 以外は常に「利用可能」を返す。

ブラウザ拡張（Windows のみ）

WebView2 の拡張機能 API で Chrome/Edge の拡張を読み込む。状態は browserExtensions キー（バックアップ対象外）。 追加フォルダの _ 始まり予約名エントリは WebView2 が拒否するため、除外コピー（サニタイズ）を作って読み込む。 状態の読み書きと reconcile（desired state を各プロファイルへ反映）は 1 つの Mutex で直列化。 Windows 以外の全コマンドは extension.unsupported を返す。macOS/Linux を見送った理由は browser-extensions-notes.md。

inject の組み立て

inject/mod.rs がビルド済み inject/*.js を include_str! で束ね、設定を JSON エンコードして window グローバルに前置した init script を生成する（build_init_script / build_popup_init_script）。TS ソース（inject/_src）のビルドは npm run build:inject。実装は inject ページへ。

主要フロー

  • 起動 setup（復旧 → ストア登録 → ウィンドウ生成）
  • カラム WebView 生成 〜 inject 注入 / Android のカラム生成
  • コマンド呼び出しと ACL 判定

規約とテスト

  • テスト関数名は日本語で書く。ASCII 大文字を含めない（non_snake_case 警告が cargo clippy -- -D warnings でビルドエラーになる。英単語はすべて小文字）。
  • 静的解析：npm run lint:rust（cargo clippy --all-targets -- -D warnings）。警告は残さない。
  • テスト：cargo test --manifest-path src-tauri/Cargo.toml。事前に npm run build:inject （inject の .js を include_str! するため）。
  • ログ・expect・panic のメッセージは英語固定。
  • 純粋関数に切り出してテストする。OS 依存部（WebView2 呼び出し等）は薄く保つ。

落とし穴・関連資料

よくある事故
  • コマンド追加で build.rs / capability を更新し忘れる（実行時に ACL 拒否）。
  • Store::save を直接呼ぶ（アトミック保存をすり抜ける）。setup の復旧→ストア登録の順序を崩す。
  • desktop と mobile の片方だけを修正する（同名コマンドが 2 実装）。
  • JS の camelCase 引数に rename / non_snake_case を付け忘れる（値が届かない）。
  • 新しい WebView builder に on_new_window 等を付け忘れる／prevent_close の常駐ウィンドウに destroy を足し忘れる。
  • Linux カラムのクリッピング変更をテストなしで行う（過去に複数回デグレ）。
  • Mutex を保持したまま await する／ロック順序（registry → compose）を崩す。
  • 設定の既定値を Rust だけ変える（TS と fixture の 3 点同期が必要）。
