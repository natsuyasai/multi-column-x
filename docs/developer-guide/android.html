Android ネイティブ層（Kotlin）

Android 版でだけ必要になる「ネイティブ側の仕事」を担う層です。カラムの WebView をどう並べるか、アカウントごとのセッション分離、スワイプバー、ファイル選択、動画ダウンロード、APK 自己更新、バックアップを、Rust・JS とどう受け渡しているかを説明します。

対象ディレクトリ

src-tauri/gen/android/ のうち、手書きの Kotlin は src-tauri/gen/android/app/src/main/java/com/natsuyasai/multicolumnx/ 直下です。その中の generated/ は Tauri が自動生成するコードで、編集してはいけません（ktlint の対象外です）。Rust 側の相手方は src-tauri/src/android_bridge.rs です。

前提知識

Android や Tauri の Android 対応に慣れていない人向けに、このページを読むための最低限をまとめます。

用語 このプロジェクトでの意味
Activity Android の「画面」の単位。本アプリは MainActivity（メイン）と AddAccount（ログイン専用）の 2 つを使う。
WebView アプリ内にウェブページを表示する部品。React UI も、X を表示する各カラムも、すべて別々の WebView。
Tauri Android の仕組み Rust コードは共有ライブラリ（.so）としてビルドされ、Kotlin の Activity が起動時に読み込む。Activity が React UI の WebView をホストする。
JNI Rust→Kotlin は call_method でメソッド名を文字列指定して呼ぶ。Kotlin→Rust は external fun と、Rust 側の Java_com_..._AppBridge_xxx が対応する。
addWebMessageListener JS から window.xxx.postMessage(文字列) でネイティブへ送る仕組み。送信元オリジンを限定できる。本プロジェクトの JS→Kotlin ブリッジはこれを使う（addJavascriptInterface は使わない）。
Foreground Service 通知を出し続けることで、アプリが裏に回っても OS に kill されにくくするサービス。動画 DL で使う。
SAF（Storage Access Framework） OS 標準のファイル保存/選択ダイアログ。権限なしでユーザー指定の場所に読み書きできる。
BackupAgent OS の Auto Backup（端末引き継ぎ）に何を含めるかを決めるクラス。
Gradle / ProGuard(R8) / ktlint ビルドツール / リリースビルドでの難読化・縮小 / Kotlin の整形・静的検査。R8 は文字列で呼ばれるメソッド名を勝手に変えるので、keep ルールが要る。

外部設計: Android 層の責務

デスクトップではカラムが独立した Tauri の WebView として作られますが、Android では window.add_child() が使えません。そこでこの層がネイティブの WebView を Activity の画面に直接重ねてカラムを表現します。

項目 デスクトップ Android
カラムの表示 Rust が子 WebView を作る Rust が JNI で createColumnWebView を呼び、Kotlin が View として重ねる
X ページ側の IPC Tauri の invoke が使える 使えない。代わりに addWebMessageListener ブリッジ→JNI→Rust
アカウント分離 data_directory WebView Profile API（非対応端末は Cookie の付け替え）
アカウント追加 URL ポーリング（tokio） 別 Activity + センチネルファイル
自動更新 Tauri updater 自前の APK ダウンロード・検証・インストール
戻るキー・スワイプバー・ファイル選択・動画 DL 通知 なし／別実装 この層が実装
JS を介さない理由

メイン React の WebView の JS は、AddAccount など別 Activity が前面にいる間 Android に suspend されます。そのため重要な完了通知は JS ではなく、ファイル（センチネル）と tokio ポーリングで行います。

ファイルによる通知（センチネル）

アカウント追加・再認証（AddAccount）

  • Rust の open_add_account_window（mobile 版）が新しい accountId を作り、JNI で launchAddAccount を呼びます。以降はブロックしてセンチネルの出現を待ちます（最大 10 分）。
  • AddAccount は x.com/login を表示し、500ms ごとに location.pathname を JS 評価します。X は SPA で pushState 遷移のため、onPageStarted では検知できません。
  • 成功すると Cookie のスナップショット（x_cookies.txt）を保存し、twid Cookie から X ユーザー ID を取り出して、センチネルの本文に書きます。戻るキーはページ遷移中は無視し、戻れる履歴があれば WebView 内を戻ります。
  • 再認証（mode=reauth）は一時プロファイル reauth-tmp-{uuid} で再ログインさせ、expectedUserId と一致した時だけ本番プロファイルへ Cookie を転記します。不一致・取得不能は reauth_mismatch（なりすまし防止）。

WebView プロファイルとセッション分離

WebViewProfiles が Profile API（WebViewFeature.MULTI_PROFILE）の対応判定と適用を担当します。プロファイル名は account-{accountId}、AddAccount・カラム・ポップアップは同じ名前を共有して同一セッションになります。

  • WebView 生成直後に setProfile（使用前でないと失敗する）。
  • サードパーティ Cookie 許可（api.x.com の 401 対策）はプロファイル側の CookieManager に設定。
  • プロファイル初回作成時のみ、旧 x_cookies.txt から Cookie を移行。
  • CookieManager が全アカウント共有になる。
  • loadUrlForAccount が removeAllCookies の完了コールバック内で Cookie を設定してから loadUrl（順序を崩すと Cookie 未設定でロードが始まる）。
  • アクティブカラムの切替時は setAccountCookies で付け替える。
ログイン画面が出たら

Cookie 反映のタイミング次第でログイン画面が一瞬表示されることがあります。ExternalLinkWebViewClient が検知して、1.5 秒後に元 URL へ 1 回だけリカバリします。

バックアップ復元の自動候補に使う detectXUserId も、プロファイルの CookieManager から twid を読みます。非対応端末ではアカウントを特定できないため空文字を返します。

スワイプバー

カラム下端の横スワイプ領域は、SwipeBarOverlayView（ネイティブ View）で実装しています。WebView より手前に置くことで、X ページへのタッチを奪わずに独自ジェスチャーを処理するためです。

  • 位置は Gravity ではなく絶対座標（yDp）。IME 表示・回転でカラムとずれないよう、カラムと同じ計算元を使う。
  • 判定ロジックは SwipeGestureResolver に分離（方向・タップ・ダブルタップ 300ms）。React 版 MobileSwipeBar のしきい値と揃える。
  • Kotlin は onSwipeNavigate / onSwipeProgress / onSwipeDoubleTap を JNI で通知するだけ。実際にカラムが遷移するかは React が決め、遷移した時のみ setSwipeBarFlash（演出）が戻ってくる。
  • Z 順は restoreOverlayOrder() に集約：popup > スワイプバー > カラム > メイン。
  • 配色は src/index.css のトークンを Kotlin に複製しているため、 src/lib/swipeBarColors.contract.test.ts が値の一致を検査する。

ファイル選択・動画ダウンロード

ファイル選択

ネイティブ WebView は onShowFileChooser を実装しないと <input type="file"> が無反応です。MainActivity が SAF の Intent を起動し、結果を filePathCallback に返します。

  • 複数 MIME は EXTRA_MIME_TYPES で渡す（createIntent() は先頭 1 件しか type に反映しない）。
  • Google フォト等は結果を clipData にだけ入れるため、pickChooserUris が clipData を優先し、無い場合のみ parseResult にフォールバック。
  • キャンセル時や選択アプリ無しは必ず null で解決する（さもないと以降のファイル選択が無反応になる）。

動画ダウンロード

長押しメニュー（inject）→ブリッジ→Rust がダウンロード→Kotlin が SAF 保存、が基本経路です。ダウンロード中は VideoDownloadForegroundService が通知を出して延命します。詳しくは「フロー」のステップ再生を参照。

  • 通知文言は res/values/strings.xml（既定=英語）と values-ja。端末の言語に従い、アプリ内 language 設定とは独立。
  • Android 13+ の POST_NOTIFICATIONS は許可リクエスト UI を作らず、許可されていれば通知が出る方針。

APK 自己更新・バックアップ

APK 自己更新

Rust の install_apk_update が URL・呼び出し元を検証して JNI で downloadAndInstallApk を呼びます。Kotlin は「不明なアプリのインストール」許可→別スレッドで DL→ApkHashVerifier で SHA-256 照合→FileProvider 経由でインストーラ起動、の順です。ハッシュ不一致ならファイルを削除して中止します。同一署名でないと上書き更新は失敗します。

バックアップ

  • ファイルの書き出し/読み込み（エクスポート/インポート機能）: Rust が startBackupExport / startBackupImport を呼び、SAF の結果を AppBridge.onBackupFileResult で非同期に Rust へ返す。インポートは上限バイトで打ち切り （copyWithLimit）、Rust 側でも再検査。
  • 端末引き継ぎ（Auto Backup）: MultiColumnXBackupAgent.onFullBackup が BackupFileSelector で選んだファイルだけを送る。Service Worker など巨大で再生成可能なディレクトリを除外しないと、25MB クォータ超過でバックアップが丸ごと失敗する。
  • AndroidManifest.xml の android:fullBackupOnly="true" が必須。無いと onFullBackup が呼ばれず、成功を返すのに空の復元になる。

詳細: backup-restore-notes.md

セキュリティ（ブリッジのオリジン検証）

X を表示する WebView に、ネイティブ呼び出し口を開けるのは危険です。そこで次の多重防御を行っています。

  1. shouldExposeBridge: WEB_MESSAGE_LISTENER 非対応端末ではブリッジを一切公開しない。
  2. BRIDGE_ALLOWED_ORIGIN_RULES: https://x.com、https://*.x.com、twitter.com 同様のみ許可（WebView 内部のフィルタ）。
  3. コールバック内で isMainFrame を確認（iframe は拒否）し、isAllowedBridgeOrigin で再検査。 x.com.example.com のような偽装ホストはホスト名の完全一致/サブドメイン判定で拒否。
  4. parseBridgeMessage: 不正 JSON・未知の type・必須フィールド欠落/空は null → 無視。
  5. APK 更新は Rust 側で呼び出し元（main のみ）・URL（自リポジトリ Releases のみ）を検証し、Kotlin 側で SHA-256 を検証。
addJavascriptInterface を使わない

オリジン制限ができず、任意のページから呼べてしまうため採用しません。新しいブリッジも addWebMessageListener と同じ検証パターンで追加してください。

MainActivity.kt のシグネチャを変えたら proguard-rules.pro も同時に更新

Rust は env.call_method で名前を文字列指定して呼びます。デバッグビルドは R8 が無効のため通りますが、リリースビルドでだけ NoSuchMethodException でカラムが作れなくなります。メソッド追加→ -keepclassmembers にエントリ追加、引数変更→型リスト更新、削除→エントリ削除。JNI 関連の変更は必ずリリースビルドで確認します。

落とし穴・関連資料

  • WebviewWindowBuilder::build() 直後に IPC ルーティング先が新規 Activity に移るため、Rust は Ok を先に返す設計になっている（android-notes.md）。
  • カラム WebView の初期 visibility は INVISIBLE。GONE だとビューポートサイズが伝わらず、X の仮想リストが壊れる。
  • 同一 id のカラムが既にある場合 createColumnWebView は再作成しない（React がリロードされてもネイティブ側は残る）。
  • registerForActivityResult は Activity 生成前（プロパティ初期化子）で登録。onCreate 内だと実行時エラー。
  • デスクトップの外部リンク処理（on_new_window）とは別で、Android は ExternalLinkWebViewClient / ExternalLinkWebChromeClient が x.com 以外をシステムブラウザへ渡す。
  • 新しい JS ブリッジを足すと column には元々 Tauri IPC が無いので、PopupSessionBridge の転用はできず、createColumnWebView 内で個別に登録する。
  • 実機の複数アカウント分離は、Profile API 非対応端末では確実でない可能性がある。
