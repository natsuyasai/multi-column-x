機能追加ハウツー

手作業で機能を足す・変えるときの手順書です。各レシピは「いつ使うか → 流れ → チェックリスト → 確認方法 → よくあるミス」の順で、チェック状態はブラウザに保存されます。Claude Code を使わない場合も、.claude/skills/ の手順書は人間が読んでそのまま使えます。

最初に知っておくこと

このプロジェクトは「同じ事実が複数の場所にある」箇所（コマンド名・既定値・辞書・色）を契約テストで守っています。チェックリストの最後は必ず「どのテストが落ちるか」を確認する形にしてあり、変更の途中で何度か実行すると漏れに早く気づけます。

1. 開発を始める前に

いつ使う: 初めてリポジトリを触るとき、または新しい作業を始める前。

チェックリスト

  1. 環境を用意する
    Node.js（npm）、Rust ツールチェーン、Tauri の前提ソフトを入れ、npm install を実行。Android は Android Studio / NDK も必要です（ビルド時に ANDROID_NDK_HOME が無いと reqwest 系で失敗）。入口は README.md、技術詳細は docs/development/project-structure.md。
  2. inject を一度ビルドする
    npm run build:inject。Rust は生成済みの inject .js を include_str! で埋め込むため、新しい clone / worktree ではこれが無いと cargo がコンパイルできません。
  3. 作業ブランチを切る
    develop を最新化 → develop から作業ブランチ → 完了後に push → develop 向け PR。新規ブランチを切るかは着手前に確認するのが決まりです（CLAUDE.md）。1 回の作業では 1 つのことだけを行い、作業の粒度ごとにコミットします。
  4. 要求を明確にし、Gherkin で仕様を書く
    機能追加・挙動変更・バグ修正では docs/specs/ に日本語 Gherkin の仕様を書いて承認を得ます（挙動不変のリファクタ・docs・CI 設定のみの変更は不要）。手順は .claude/skills/gherkin-spec/SKILL.md。
  5. テストを先に（または仕様由来なら後に）書く
    TDD（t-wada 流）が基本。Gherkin 由来のテストだけは実装後でも構いませんが、主要な分岐を壊して Red になるか確かめるミューテーション確認は必須。テスト名は日本語、Rust のテスト関数名には ASCII 大文字を入れない。 .claude/skills/tdd/SKILL.md
  6. テストに .feature への参照を書かない
    テストコード・コメント・コミットメッセージに仕様ファイルへの言及を残さず、.feature 自体もコミットしません。

確認方法

変更ごとに下のコマンドを実行します（全体は 10 章）。いずれもリポジトリ直下で実行します。

コマンド 何を守るか
npm run format TS / Rust / Kotlin の整形（TS のみは format:ts）
npm run typecheck 型エラー（tsc --noEmit）
npm run lint ESLint（src の TS/TSX）。自動整列は lint:fix
npm test Vitest 単体テスト（契約テスト含む）
よくあるミス

build:inject を忘れて Rust のテストが落ちる／Gherkin を書かずに実装に入る／新ブランチを確認なしに作る／コミット前にミューテーション確認をしていない。

参考: feature-development-flow（全体フロー）、 check-creation （品質チェック一式）。

2. Tauri コマンドを追加・削除する

いつ使う: React から Rust の処理を呼びたいとき（invoke の相手を増やす）。

登録先は 4 点セット

src-tauri/src/lib.rs の generate_handler! / src-tauri/build.rs の AppManifest / src-tauri/capabilities/default.json（X ページから呼ぶなら src-tauri/capabilities/column-webview.json）/ contracts/ipc-constants.json を必ず同時に更新します。削除も同じ 4 点です。

チェックリスト

  1. Rust にコマンド関数を書く
    src-tauri/src/commands/ 配下の適切なモジュール（例: src-tauri/src/commands/settings.rs）に #[tauri::command] を付けて実装し、commands/mod.rs からモジュールを公開します。失敗は文章でなく AppError （src-tauri/src/commands/app_error.rs）で返す。
  2. デスクトップ専用／モバイル専用なら cfg を付ける
    #[cfg(desktop)] / #[cfg(mobile)] で実装が分かれる場合は両方を確認。generate_handler! 側のコマンド名の直前にも同じ属性が必要です（付け忘れると Android ビルドで失敗）。
  3. 引数・戻り値の serde 名を揃える
    Tauri v2 は JS→Rust のケース変換をしません。JS 側 camelCase のフィールドには #[serde(rename = "...")] が必要。
  4. メイン専用なら require_main_caller を呼ぶ
    破壊的な操作は require_main_caller(&webview) で呼び出し元を検証（src-tauri/src/commands/mod.rs）。
  5. lib.rs の generate_handler! に登録
    src-tauri/src/lib.rs の .invoke_handler(tauri::generate_handler![...]) に追加。
  6. build.rs の AppManifest にコマンド名を追加
    src-tauri/build.rs の一覧に（cfg 付きコマンドも含めて）追加。無いとどの capability でも拒否されます。
  7. capability に allow-<kebab-case> を追加
    メインウィンドウ向けは src-tauri/capabilities/default.json。inject（X のページ）から呼ぶコマンドだけ src-tauri/capabilities/column-webview.json にも足します（許可集合は inject が実際に使うコマンドと厳密一致で検証される）。
  8. IPC 定数を 3 箇所にそろえる
    src/constants/ipc.ts（IPC_COMMANDS）、 src-tauri/src/ipc_constants.rs、 contracts/ipc-constants.json。
  9. TS のラッパーを services に書く
    invoke(IPC_COMMANDS.XXX, 引数) を呼ぶ薄い関数を src/services/（例: src/services/extensions.ts）に置き、フックや UI から使います。失敗の表示には describeAppError （src/lib/appError.ts）を使う。
  10. Rust 側と TS 側のテストを書く
    Rust の純粋なロジックは #[cfg(test)] でテスト（関数名に ASCII 大文字を使わない）。services はモックした invoke でテスト。
  11. 契約テストを通す
    npm run build:inject → cargo test --manifest-path src-tauri/Cargo.toml（src-tauri/src/acl_contract.rs と ipc_constants.rs）、npm test（src/constants/ipc.contract.test.ts）。

確認方法・守ってくれるテスト

  • src-tauri/src/acl_contract.rs: 全コマンドが AppManifest と capability に載っているか、X 向け capability の許可集合が inject の使用集合と一致するか、メイン向け capability に remote が無いか。
  • src-tauri/src/ipc_constants.rs / src/constants/ipc.contract.test.ts: 定数と fixture と lib.rs 登録の一致。
よくあるミス

build.rs だけ直して capability を忘れる／mobile でだけ cfg の付け忘れでビルドが落ちる／serde の rename 忘れで引数が undefined として届く／column-webview.json にメイン専用コマンドを足してしまう。

詳細: tauri-commands.md、architecture-overview.md

3. 設定項目を追加する

いつ使う: 設定画面にオン/オフや数値などの項目を足すとき。X の画面の挙動に反映させたい（inject に渡す）場合は特に漏れが出やすい。

経路は 2 種類

グローバル設定は settings_store.rs の column_script_settings_from 経由、カラム個別設定は build_column_init_script 内で column.settings.* から直接 InitScriptParams へ渡ります（この場合は settings_store.rs の手順は不要）。

チェックリスト

  1. TS の型と既定値を追加
    src/types/index.ts の GlobalSettings（または ColumnSettings）と DEFAULT_GLOBAL_SETTINGS（DEFAULT_COLUMN_SETTINGS）。
  2. Rust の設定構造体と impl Default を追加
    src-tauri/src/commands/settings.rs の GlobalSettingsData（または ColumnSettings）に #[serde(rename = "camelCase名")] 付きで追加。構造体レベルの #[serde(default)] があるので、フィールドごとの #[serde(default = "...")] は付けず、impl Default を唯一の既定値とします。
  3. contracts/default-settings.json に既定値を追加
    contracts/default-settings.json。Rust / TS / fixture の 3 箇所を同時に更新するのが決まりです。
  4. 設定 UI を足す
    グローバルなら src/components/AppSettingsPanel/GeneralSettingsSections.tsx など該当セクション、ドラフトの扱いは src/components/AppSettingsPanel/settingsDraft.ts。カラム個別は src/components/SettingsPanel/。画面文言は 4 章に従い辞書化する。
  5. 保存経路を確認する
    保存は src/store/useAppStore.ts から save_settings へ。Rust 側は Store::save を直接呼ばず save_store_atomically を使う（settings-file-crash-safety-notes.md）。
  6. バックアップに含めるか判断する
    GlobalSettingsData に項目を足すと src-tauri/src/commands/backup/format_tests.rs のキー集合テストが失敗し、取捨の判断を強制されます。端末依存の項目は除外一覧に、移行したい項目は src-tauri/src/commands/backup/format.rs のホワイトリストに足します（backup-restore-notes.md）。
  7. inject に渡す場合: 配線 4 箇所を足す
    src-tauri/src/commands/settings_store.rs（グローバル設定のみ）→ src-tauri/src/commands/webview/column.rs の build_column_init_script → src-tauri/src/inject/mod.rs の InitScriptParams と window.__multiColumnXConfig → src-tauri/src/inject/_src/types.d.ts の MultiColumnXConfig。
  8. テストを書く
    正規化・変換ロジックの単体テスト。UI は *.test.tsx。

確認方法・守ってくれるテスト

  • src/types/defaults.contract.test.ts と Rust の default_settings_match_contract_fixture（src-tauri/src/commands/settings.rs）: 既定値 3 点の一致。
  • format_tests.rs: バックアップのキー集合（出力キー ∪ 除外一覧 ＝ 既定値のキー集合）。
よくあるミス

既定値を 1 箇所だけ変える／フィールドに serde(default = ...) を付けて既定値を二重定義する／inject に渡す経路のどこかを忘れ値が常に既定値になる／バックアップ判断を後回しにしてテストが落ちる。

4. 画面文言を追加する

いつ使う: ボタン・見出し・エラーメッセージなど、利用者に見える文字を足すとき（日本語・英語の両方）。

  1. ja の辞書にキーを追加
    src/locales/ja/ の該当名前空間 JSON に、camelCase のネストでキーを追加（例: settings.general.xxx.label）。名前空間は common / settings / columnSettings / columns / topbar / mobile / accounts / dialogs / rateLimit / messages（i18n-notes.md）。
  2. en の辞書に同じキー・同じ補間変数で追加
    src/locales/en/。補間は {{name}}、件数は key_one / key_other。用語は i18n-notes.md の用語集に合わせ、新しい訳語は用語集に追記。
  3. コードで t("ns:key") を使う
    useTranslation() は引数なしで呼び、必ず名前空間付きの完全キーで参照。要素を含む文は <Trans>、属性（title / aria-label / placeholder / alt）も辞書化。React 外は呼び出し時に i18n.t、純粋関数は t を引数で受ける。
  4. 新しい名前空間なら登録する
    src/i18n/index.ts の ns と src/i18n/resources.ts（ja・en 両方）。
  5. 英語表示のテストを書く
    i18n.changeLanguage("en") して描画し src/test-utils/japanese.ts の expectNoJapanese で日本語の残りを検出。テスト後は言語を ja に戻す。
  6. 契約テストを通す
    npx vitest run --project unit src/i18n。
  1. 辞書は i18next ではなく __mcxI18n に足す
    src-tauri/src/inject/_src/i18n.ts が window.__mcxI18n を公開します。各 inject は window.__mcxI18n.t("key") で引き、ES import はしない （各スクリプトを include_str! で連結するため）。
  2. X の画面と照合する日本語は翻訳しない
    「広告」などは src-tauri/src/inject/_src/i18n.contract.test.ts の許可リストに理由付きで載せます。
  1. Rust は文章を返さない
    エラーは codes に area.camelCase 定数を追加（src-tauri/src/commands/app_error.rs）→ messages.json の rustError.<area>.<name> に ja・en を追加。詳細メッセージは detail に。
  2. ウィンドウタイトル等は ui_text に追加
    src-tauri/src/commands/ui_language.rs の UiText にバリアントと ja/en を追加。開発者向けログは固定の英語 （日本語を含めると src-tauri/src/log_language_contract.rs が検出）。

確認方法・守ってくれるテスト

  • src/i18n/resources.contract.test.ts: ja/en のキー集合・補間変数の一致。
  • src/i18n/unusedKeys.contract.test.ts: 辞書の未使用キーを失敗にする。動的キーは ``t(`ns:prefix.${x}`)`` のように名前空間付き接頭辞を先頭に。
  • ESLint の no-restricted-syntax（eslint.config.js、src/lib/i18nLint.contract.test.ts）: 画面コードへの日本語直書きをエラー化。
  • src/lib/appError.contract.test.ts: Rust の全エラーコードが辞書にあること。
よくあるミス

useTranslation("settings") のように名前空間を引数に渡す（使わない）／モジュール直下の定数に翻訳結果を入れて言語切替に追従しない／日本語文言を一字でも変えてしまう／Rust が日本語文字列を返す。

5. React コンポーネントを追加する

いつ使う: 画面部品（ダイアログ・設定パネル・バー等）を新設するとき。雛形は component-create と、Story 駆動の進め方はstorybook-dev。

チェックリスト

  1. 同じディレクトリに 4 ファイルをコロケーション配置
    src/components/<Name>/ に <Name>.tsx / .module.scss / .test.tsx / .stories.tsx。バレル（index.ts）は作らず、import は各ファイルを直接指す。例: src/components/MobileTabBar/MobileTabBar.stories.tsx。
  2. UI の寸法は rem で書く
    アプリ UI の倍率は <html> の font-size で変わるため px は禁止（1px 以下のヘアラインと media query を除く）。ネイティブ WebView の bounds に使う高さは src/lib/gridLayout.ts の rem 定数と remToPx。SCSS と同値に保つ（ui-scale-notes.md）。
  3. 配色は CSS トークンを使う
    src/index.css のトークン（--mcx-*）。白文字を載せる塗り背景は --mcx-accent-fill。
  4. パネル型ダイアログなら Android 全画面ミキシン
    src/styles/_dialog-fullscreen.scss の android-fullscreen-overlay / android-fullscreen-panel($padding)（panel 全体がスクロールする構造なら android-fullscreen-sticky-header）を @include。 小さな確認ダイアログは全画面化しない。
  5. 文言は辞書化する
    4 章のとおり。日本語直書きは ESLint でエラーになる。
  6. 単体テストと Story を書く
    テスト名は日本語。Story は play function で操作を検証し、テーマは document.documentElement の data-theme で切り替える。コールバックは fn()。
  7. import 順を守る
    外部パッケージ → vitest/storybook → @/ → 相対パス、各グループ内はアルファベット昇順、グループ間に空行を入れない。npm run lint:fix で自動整列。新規コードは @/ エイリアス（@/* → src/*）を使う。
  8. 共通のフック・状態に載せるか判断する
    アプリ状態は src/store/useAppStore.ts （Zustand）、副作用は src/hooks/ のフックに切り出す。カラム WebView は OS ネイティブのため z-index が効かない点に注意（column-layout-notes.md）。

確認方法

  • npm run lint（警告も残さない）／npm test／npm run test:story（chromium でブラウザ実行。Story を追加・変更したら必須）。
  • 目視確認は npm run storybook。Storybook は index.css を読まないため、テーマ変数が必要な検証には注意。
  • src/lib/gridLayout.contract.test.ts: SCSS の高さと rem 定数の一致。
よくあるミス

px で寸法を書き表示サイズ設定に追従しない／Android でダイアログが見切れる（ミキシン未使用）／バレルを作る／ Story を作らず test:story が通らない。

6. inject 機能を追加する

いつ使う: X（x.com）のページの中で動く処理を足すとき（広告非表示・NG ワード等）。生成物の .js は直接編集しない。詳細は inject-ipc-shortcuts-notes.md と inject-script-dev。

チェックリスト

  1. _src に TypeScript を書く
    src-tauri/src/inject/_src/<name>.ts。テストは同ディレクトリに <name>.test.ts（vitest + jsdom）。DOM の監視は src-tauri/src/inject/_src/dom_observer.ts の共通ハブを使う。
  2. ビルド対象に登録する
    vite.inject.config.ts の plainEntries に名前を追加。 npm run build:inject で src-tauri/src/inject/<name>.js が生成される（gitignore 済み）。
  3. mod.rs で組み込む
    src-tauri/src/inject/mod.rs の build_init_script で include_str!("<name>.js") して連結。モバイル専用／デスクトップ専用は include_if(...)。
  4. 設定フラグを配線する（必要なら）
    3 章の経路。window.__multiColumnXConfig から読む。型は src-tauri/src/inject/_src/types.d.ts。
  5. Rust のコマンドを呼ぶ場合は ACL も更新
    inject から呼ぶコマンド名は src-tauri/src/inject/_src/constants.ts （INJECT_COMMANDS）に載せ、2 章の 4 点セットに加えて src-tauri/capabilities/column-webview.json へ。Android のカラムはネイティブ WebView で Tauri IPC が無く、JS ブリッジ経由（8 章）。
  6. キーボードショートカットなら 3 箇所を同期
    src/hooks/useKeyboardShortcuts.ts（メインフォーカス時の keydown と、WebView からのイベント受信側の switch）と src-tauri/src/inject/_src/keyboard_shortcut.ts。
  7. 実 DOM で検証する
    X の DOM は頻繁に変わり、jsdom の合成 DOM だけでは保証できません。実 X ページでの確認が必要かを依頼者に確認し、必要なら完了前に検証する。判明した恒久的な知見は inject-ipc-shortcuts-notes.md に追記。

確認方法

  • npm run build:inject が成功し、npm test がグリーン。
  • Rust も変更したら cargo test --manifest-path src-tauri/Cargo.toml と npm run lint:rust（build:inject の後に）。
  • src-tauri/src/inject/_src/i18n.contract.test.ts: inject の辞書契約。
よくあるミス

生成された .js を直接編集して次のビルドで消える／ plainEntries か include_str! の片方だけ足す／inject から ES import して連結が壊れる。

7. WebView builder を新設・変更する

いつ使う: カラム・ポップアップ・コンポーズなど、Rust で WebView（ウィンドウ）を作る処理を足す・変えるとき。

契約テストが検査する必須項目

builder を足したら、以下を付け忘れるとテストが落ちる（または実機で不具合になる）。実装は src-tauri/src/commands/webview/ の column.rs / compose.rs / popup.rs。

チェックリスト

  1. .on_new_window(external_link::new_window_handler(app.clone())) を付ける
    新規ウィンドウ要求を受け、http/https/mailto/tel だけ既定ブラウザで開き常に Deny する。 src-tauri/src/commands/webview/external_link.rs。理由と CDP での実機検証手順は external-link-new-window-notes.md。
  2. .disable_drag_drop_handler() を付ける
    Windows で Tauri 既定のファイルドロップ処理が X ページの HTML5 DnD を横取りするのを防ぐ。
  3. Windows 用に browser_extensions_enabled(true) を付ける
    アカウントの data_directory を使う全 builder に #[cfg(windows)] で付ける（食い違うと ERROR_INVALID_STATE）。 src-tauri/src/commands/webview/mod.rs の契約テストが検査。 詳細は browser-extensions-notes.md。
  4. desktop / mobile の分岐を確認する
    同一コマンド名でも #[cfg(desktop)] / #[cfg(mobile)] で実装が別。Linux のカラムは独立ウィンドウで親クリップが効かないため linux_column_layout（src-tauri/src/commands/webview/column.rs）で制御する。変更時は linux-column-spec.md と linux-webview-notes.md のテスト方針に従う（過去に何度もデグレードした領域）。
  5. prevent_close を使う常駐ウィンドウなら destroy() を追加
    close() は効かないため、メインウィンドウの CloseRequested（src-tauri/src/lib.rs）に明示 destroy() を足す。詳細は compose-popup-topbar-notes.md。

確認方法

  • npm run build:inject → cargo test --manifest-path src-tauri/Cargo.toml（webview/mod.rs の契約テスト: external_link::new_window_handler の数、拡張機能フラグ等）／npm run lint:rust。
  • CI の Rust ジョブは ubuntu のみ。#[cfg(windows)] や macOS 向けコードはローカルの clippy / test が唯一の検証になる。
よくあるミス

ポップアップ用 builder にだけ on_new_window を付け忘れ、X 内のリンクがアプリ内の新規ウィンドウで開く／ 常駐ウィンドウを足したのにアプリ終了後もプロセスが残る。

8. Android ネイティブ機能を追加・変更する

いつ使う: Kotlin 側（src-tauri/gen/android/）で端末の機能を使う処理を足す・変えるとき。 Android のカラム／ポップアップ WebView は Tauri の IPC が使えず、JS ブリッジ（JavaScript と Kotlin をつなぐ入口）を通ります。

チェックリスト

  1. Kotlin に処理を書く
    src-tauri/gen/android/app/src/main/java/com/natsuyasai/multicolumnx/MainActivity.kt または専用クラス。純粋に切り出せるロジックは JVM 単体テストが書ける形（例: BackupFileSelector）にする。
  2. Rust から呼ぶなら android_bridge.rs にラッパーを足す
    src-tauri/src/android_bridge.rs が JNI の env.call_method() でメソッド名とシグネチャを文字列指定で呼ぶ。Kotlin 側のシグネチャと完全に一致させる。 Kotlin → Rust の通知は Java_com_natsuyasai_multicolumnx_AppBridge_* の extern "C" 関数。
  3. proguard-rules.pro を同時に更新する
    MainActivity.kt のメソッドシグネチャを変えたら、 src-tauri/gen/android/app/proguard-rules.pro の -keepclassmembers を同じ型で追加・更新・削除。デバッグでは R8 が無効で症状が出ず、リリースビルドでだけ NoSuchMethodException になる。
  4. JS ブリッジはオリジンを検証する
    addJavascriptInterface は任意オリジンから呼べてしまうため、新規ブリッジは WebViewCompat.addWebMessageListener を使い、許可オリジン (src-tauri/gen/android/app/src/main/java/com/natsuyasai/multicolumnx/BridgeOrigins.kt の BRIDGE_ALLOWED_ORIGIN_RULES) とコールバック内の isAllowedBridgeOrigin で二重チェックする（メインフレームのみ受理、メッセージは src-tauri/gen/android/app/src/main/java/com/natsuyasai/multicolumnx/BridgeMessage.kt でパース）。既存の MainActivity.kt の実装に倣う。
  5. 利用者に見える文言は文字列リソースに
    src-tauri/gen/android/app/src/main/res/values/strings.xml （既定=英語）と src-tauri/gen/android/app/src/main/res/values-ja/strings.xml に同じキーを追加。書式付きは %1$d の位置指定子、コードは getString(R.string.…)。端末の言語に従い、アプリ内の language 設定とは独立。
  6. 権限・Manifest を確認する
    Foreground Service は Android 14 以降 foregroundServiceType の明示が必須。バックアップ対象は data_extraction_rules.xml 等（ワイルドカード非対応）。詳細は android-notes.md。
  7. 単体テストを書き Gradle で実行する
    テストは src/test/java/com/natsuyasai/multicolumnx/（例: BridgeOriginsTest.kt / StringResourcesTest.kt / MainActivityTest.kt）。

確認方法

cd src-tauri/gen/android && ./gradlew.bat :app:testUniversalDebugUnitTest
  • testDebugUnitTest では app のテストが実行されない（universal フレーバー付きのため）。必ず :app:testUniversalDebugUnitTest。
  • Kotlin の整形は npm run format:kotlin（ktlint）。新しい git worktree には gitignore 済みの生成ファイルが無いので、先に tauri android 系コマンドで生成する（android-notes.md）。
  • リリースビルド（npm run tauri:android:build）で実機動作を確認する。
よくあるミス

proguard-rules.pro の更新漏れ（リリースだけクラッシュ）／英語の既定側に日本語を直書き／ registerForActivityResult を onCreate 後に登録する（プロパティ初期化子で行う）。

9. 配色トークンを変更する

いつ使う: アプリ UI の色（ライト/ダーク）を変えるとき。

チェックリスト

  1. index.css のトークンを変更する
    src/index.css の :root / :root[data-theme="dark"] / :root[data-theme="light"] の値を、該当する全ブロックで更新。
  2. 白文字を載せる塗り背景は --mcx-accent-fill を使う
    --mcx-accent を背景にすると白文字が読めない。新規の塗りボタンは --mcx-accent-fill。
  3. コントラスト基準を満たす
    src/lib/themeContrast.contract.test.ts （計算は src/lib/contrast.ts）。
  4. Android のスワイプバーの色を同期する
    src-tauri/gen/android/app/src/main/java/com/natsuyasai/multicolumnx/SwipeBarOverlayView.kt に複製した色を、src/lib/swipeBarColors.contract.test.ts が一致を検証する。
  5. Storybook / 実機で目視する
    Storybook は index.css を読み込まないため、トークンの検証は実アプリまたは Story 側でトークンを定義して確認。

確認方法

npx vitest run --project unit src/lib/themeContrast.contract.test.ts src/lib/swipeBarColors.contract.test.ts または npm test。テーマ切替の仕組みは release-theme-reauth-notes.md。

よくあるミス

ライトだけ直してダークを忘れる／Kotlin の複製色を更新せず契約テストが落ちる。

10. 完了前の最終チェック

いつ使う: PR を出す前。変更した層に応じて、上から順に実行しエラー・警告を 0 にします。

  1. npm run format
    TS / Rust / Kotlin をまとめて整形。
  2. npx prettier --check .
    CI（.github/workflows/ci.yml）と同じ。docs・md だけの変更でも必須。落ちたら npx prettier --write <対象>。
  3. npm run typecheck
    tsc --noEmit。
  4. npm run lint
    警告も残さない。自動整列は npm run lint:fix。
  5. npm test
    Vitest 単体テスト（契約テストを含む）。
  6. npm run test:story
    Story を追加・変更した場合は必須（chromium で実行）。
  7. npm run test:property
    プロパティテスト（fast-check）。仕様が明確ならまず property-based-testing を検討。
  8. npm run build:inject → npm run lint:rust → cargo test
    src-tauri/ を変更した場合。 cargo test --manifest-path src-tauri/Cargo.toml。
  9. Android のテスト・リリースビルド
    Kotlin を変更した場合は ./gradlew.bat :app:testUniversalDebugUnitTest、必要ならリリースビルド。
  10. npm run docs:build
    docs/guide/（ユーザーガイド）を変更した場合は必須。VitePress のリンク切れ検出を兼ねる。
  11. npm run build
    最終のビルド確認。
  12. 手動テスト項目を用意する
    Gherkin の @manual シナリオは手動テスト項目として integration-test.md に出力（手順は integration-test-viewpoints）。例: docs/development/backup-restore/integration-test.md。
  13. 開発者ガイドを更新する
    コマンド・設定・コンポーネント等を増減したら developer-guide-maintenance でこのガイドも追従させる。
目安

TS だけの変更なら 1〜7 とビルド、Rust を触ったら 8、Kotlin を触ったら 9 を足す、と覚えると迷いません。まとめて実行する手順は check-creation。

11. 困ったとき

症状から原因と対処を引けます。検索ボックスやチップで絞り込んでください。クリックすると詳細と関連ファイルが開きます。

まず試すこと

  1. 契約テストを先に走らせる
    npm test と cargo test --manifest-path src-tauri/Cargo.toml は「どこが食い違っているか」を名前で教えてくれます。
  2. build:inject を実行したか確認する
    inject と Rust の不具合の多くはここ。
  3. CLAUDE.md の該当節と docs/development のノートを読む
    CLAUDE.md は変更箇所ごとに参照すべきノートを示しています。
