inject スクリプト（X の画面に注入する JS）

Multi Column X は x.com をそのまま WebView で表示し、見た目や挙動の独自機能はページの中に JavaScript を差し込んで実現しています。この差し込む JS が inject です。このページでは、inject の責務と境界、ビルドから注入までの仕組み、全スクリプトの一覧、主要機能の設計判断、開発時の落とし穴を説明します。

前提知識

initialization script（ページ読み込み時に必ず走る JS）

Tauri は WebView を作るとき、initialization_script として JS 文字列を登録できます。これはページ遷移や再読み込みのたびに、ページ本体のスクリプトより先に実行されます。inject はこの仕組みで X のページに入り込みます。Rust 側が「どの機能を含めるか」を決めて 1 本の文字列に連結し、WebView に渡します。

MutationObserver と、X の DOM は変わりやすいこと

X は SPA で、タイムラインは仮想リスト（画面に見える投稿だけを描画し、スクロールで DOM を差し替える）です。そのため「読み込み時に 1 回処理して終わり」では足りず、MutationObserver で変化を追い続けます。また data-testid や構造は X の都合で予告なく変わるため、inject は常に壊れうる前提で書き、実 DOM での検証を重視します。

window.__TAURI__ と IPC

WebView 内の JS から Rust のコマンドを呼ぶ仕組みが IPC です。tauri.conf.json の withGlobalTauri: true により、ページには window.__TAURI__.core.invoke(コマンド名, 引数) が用意されます。ただし x.com のような外部ページに任意のコマンドを許すのは危険なので、許可したコマンドだけを capability で列挙しています（外部設計で後述）。

Android は別経路（ネイティブ WebView + ブリッジ）

Android のカラム／ポップアップは Tauri の WebView ではなく Android 標準の WebView なので、__TAURI__ がありません。代わりにネイティブ側（Kotlin）が addWebMessageListener で公開した __mcxPopupBridge などに postMessage(JSON) を送ります。つまり同じ機能でも desktop は invoke、Android はブリッジと書き分けられている箇所があります。

なぜビルドが要るのか／ビルド済み JS をコミットしない

ソースは TypeScript（_src/）で、Vite でビルドした src-tauri/src/inject/*.js を Rust が include_str! でバイナリに埋め込みます。出力 .js は .gitignore 対象でコミットされません。よってクローン直後や _src を変更したあとは npm run build:inject が必須です（tauri:dev / tauri:build は前段で自動実行）。

ES module の import が使えない

各 inject は独立した 1 ファイルとして出力され、Rust が単純に文字列連結します。複数のエントリが同じモジュールを import すると Rollup が共有チャンク（import 文付き）を作り、連結が壊れます。だから定数もローカルに重複定義し、共有機能は window.__mcxDomObserver / window.__mcxI18n のようなグローバル経由にしています。

外部設計

責務と境界

  • 責務：X の画面の加工（要素の非表示・拡大縮小・CSS）、X の挙動の補助（自動更新・新着検知・ポップアップ・ショートカット）、状態の Rust への報告。
  • 持たないもの：永続的な状態。設定の保存は React/Rust 側（settings.json）が持ち、inject は起動時に埋め込まれた値と、eval で渡される更新だけを受け取ります。
  • 対象 WebView：カラム（column-*）、ポップアップ（popup-*）、コンポーズ窓（compose-*）。 アカウント追加窓（add-account）は capability の対象に含まれます（inject の注入有無は 要確認）。
  • page_type による出し分け：home（前回の境目へ戻る）、compose（投稿専用表示）、external（任意 URL カラム。custom_css だけの最小注入）。

許可集合の厳密一致

src-tauri/capabilities/column-webview.json の許可は、_src で実際に invoke されるコマンド集合と 過不足なく一致することを acl_contract.rs が検査します。inject で新しいコマンドを呼ぶなら、 build.rs の AppManifest・capability・テストの期待値を同時に更新します。詳細は tauri-commands.md と inject-ipc-shortcuts-notes.md。

設定フラグの受け渡し

カラム個別設定は column.rs が column.settings.* から、グローバル設定は settings_store.rs の column_script_settings_from を通して InitScriptParams に詰め、mod.rs が window.__multiColumnXConfig に変換します。新しい GlobalSettings フラグを inject へ届けるには 7 箇所の同期（TS 型、fixture、settings.rs、settings_store.rs、column.rs、inject/mod.rs、types.d.ts）が必要です （ノートと .claude/skills/inject-script-dev を参照）。

Tauri の initialization_script に登録。image_popup / context_menu / scroll_event / keyboard_shortcut が含まれ、mobile_area_hide は含まれません。ショートカットや横スクロールはカラムがネイティブウィンドウで独立しているため inject が代わりに拾います。

is_mobile = true のとき上の 4 つは除外され、mobile_area_hide が含まれます。Rust→JS は eval_in_webview が android_bridge::eval_in_column_webview 経由で評価。JS→Rust は上述のブリッジ。

詳細設計

mod.rs：設定から 1 本の JS を組む

build_init_script は、InitScriptParams（bool 群・文字列・配列）を受け取り、include_if で機能を足し引きして連結します。連結後は1 つのスクリプトになるので、トップレベルの function / const 名が機能間で重複すると、後勝ちの上書きや SyntaxError になります（だから各機能は IIFE で囲み、複製関数は別名にします）。テストは連結順・含有・config の値を検証します。

auto_reload：更新方式の違いを吸収する

  • 検索・通知は『下へスクロール → 60ms 後に先頭へ戻す』で X の取得を誘発し、おすすめ／リストはタブの再クリック、フォロー中は focus と新着ボタンのクリック。リスト詳細は自動更新の対象外。
  • 新着判定は『見たことのある最大の status ID より新しい ID』。旧方式（スナップショット差分）は表示が入れ替わるおすすめで誤報告したため廃止。
  • 通知・検索は scroll と DOM 変化を常時監視し、X のポーリングで先頭がずれたら補正します。 共有ハブを使わないのは、描画されないカラム（Android の非アクティブタブ等）でハブが止まり新着の報告が遅れるため。
  • スクロール距離・待ち時間は実測値で、カラムの高さにも依存します。変更時は必ず再計測（詳細はノート）。

return_to_last_read：triggerReload のラップ

更新を検知するために window.__multiColumnX.triggerReload をラップするので、auto_reload より後ろに連結する必要があります。基準（更新前の先頭付近の最大 5 件）は「最後に先頭にいたときのスナップショット」を使います（手動更新は先頭へ戻すのと同じ tick で取得が始まり、その時点の仮想リストは深い位置しか描画していないため）。純粋ロジックは _logic.ts に分離され、DOM グルーと別にテストされます。

ng_word と hide_ad：隠す方法

追加された article を判定し、仮想リストのセル（cellInnerDiv + absolute + transform）はセルごと remove() して空白を残さず、それ以外は display:none !important にします。NG ワードは設定を毎回 config から読むため、eval で書き換えて recheckNgWords を呼べば即時反映されます。マッチ判定は /正規表現/ 形式にも対応した純粋関数です。

popup_toolbar：ポップアップ専用 UI

アカウント切替・閉じる・動画ダウンロード・『カラムへ適用』（公式設定の送信）・Esc で閉じる・targetHref の自動クリックを持ちます。desktop は invoke、Android は __mcxPopupBridge に投げます。ポップアップは言語の即時切替の対象外で、作成時の言語で固定されます。

header_customizer：React 製で大きい理由

表示するリンクを選ぶ独自メニューが状態を持つため React で描画します。React 本体を同梱するので生成物は約 587KB（他の数 KB〜数十 KB と桁違い）。Vite の設定でも専用の --mode react パスにして inlineDynamicImports で 1 ファイルに固めます。全カラムに入れると重いので、 ヘッダー非表示または投稿欄非表示が ON のカラムだけ Rust が連結します。設定変更時は『アンマウント → 必要なら再マウント』で整合を取ります。

動画関連

video_control は HTMLMediaElement.prototype.play を差し替えて自動再生を抑えます（X のプレイヤーは pause されると play() を再試行するため、最初の play() だけ通して 1 度止める工夫付き）。video_long_press_menu は DOM に URL が無いため React Fiber の props から動画 variants を取り出します。ダウンロードは Android ブリッジ専用です。

api_rate_limit_monitor：XHR を傍受して報告

X の内部 API の応答ヘッダ（x-rate-limit-*）を読み、バケットごとに Rust へ報告します。表示側の設計は api-rate-limit-operations-notes.md を参照。

i18n ハブ

inject の自前 UI は ja/en 対応です。辞書は i18n.ts の ja と en にあり、t は 現在言語 → ja → キー文字列の順に引きます。静的要素は apply で data-mcx-i18n* を付け、言語切替時に自動再適用されます。React 描画のものは onChange で追従します。

開発・検証

基本の流れ

  1. _src の TypeScript を編集
    テストは同ディレクトリにコロケーション（<name>.test.ts / <name>.property.test.ts）。新規機能なら vite.inject.config.ts の plainEntries にも追加。
  2. npm run build:inject
    開発起動中のアプリは再ビルドされる。Rust のテスト前にも必須。
  3. 設定フラグが要るなら 7 箇所同期
    src-tauri/src/inject/mod.rs の InitScriptParams と config_script、 src-tauri/src/inject/_src/types.d.ts の MultiColumnXConfig など。
  4. 新しい Rust コマンドを呼ぶなら ACL も同時に
    src-tauri/build.rs の AppManifest と src-tauri/capabilities/column-webview.json。
  5. テストとビルドを通す
    npm test、Rust を触ったら cargo test と npm run lint:rust。

実 DOM 検証のルール

jsdom の合成 DOM では X の実際の挙動を保証できません。新規作成や DOM 依存ロジックの変更では、実 X での検証が必要か否かを必ずユーザーに確認し、必要なら claude-in-chrome で実ページの DOM を調べてから完了とします（例：引用 RT の動画は status リンクが DOM に無く、React Fiber の tweet.id_str からしか ID が取れない、は実 DOM 調査でのみ判明）。実アプリ（WebView2）の検証手順（CDP 接続）は ノートにあります。

テストの種類

種類 何を守るか 場所／コマンド
単体（jsdom） DOM 加工・イベント処理。合成 DOM で検証 _src/*.test.ts / npm test
プロパティテスト 純粋ロジックの不変条件（fast-check） _src/*.property.test.ts / npm run test:property
i18n 契約 ja/en のキー集合・補間変数の一致、日本語直書きの検出 i18n.contract.test.ts
Rust 側 連結順・含有・config の値・ACL の厳密一致 inject/mod.rs のテスト、acl_contract.rs
X の画面と照合する日本語は許可リストに

hide_ad.ts の AD_TEXTS、notification_header_hide.ts の aria-label="通知タイムライン"、headerCustomizerTypes.ts のキー／ariaLabel などは X の画面の文言と照合する値なので翻訳しません。 i18n.contract.test.ts の許可リスト（ファイル＋部分文字列＋理由）に載せ、未使用の許可項目が残るとテストが失敗します。

ビルドを忘れたときの症状

  • Rust のビルド／テストが「ファイルが見つからない」で失敗：.js が一度も生成されていない。
  • 挙動が直らない／テストが古い JS で通る：_src を直したが build:inject していない（.js は include_str! で埋め込まれた古いまま）。
  • 新機能が動かない：plainEntries に追加しておらず .js が出力されていない、または mod.rs で連結していない。

落とし穴・関連資料

import 禁止と重複定義

共有チャンクを作る import は連結を壊します。定数は各ファイルにローカル定義し、constants.ts は参照用。Window 拡張の型もメインアプリ用と inject 用の 2 箇所があり、手動で同期します。グローバル名（__multiColumnX など）を変えるときは、型 2 箇所・各スクリプトのローカル定数・Rust の ipc_constants::globals・ipc.ts の eval テンプレート（直接埋め込み）まで見直します。

連結順と名前衝突

return_to_last_read は auto_reload より後ろ、dom_observer と i18n は最初。順序を変えるとテストが落ちます。連結後は 1 本のスクリプトなので、トップレベル名の重複に注意。

多重注入・観測ループ

ページ遷移のたびに再注入されるため、冪等に（例：dom_observer は二重生成しない、auto_reload は disposeAutoReloadWatchers で前回を解除）。自分の描画が DOM 監視に拾われて無限ループにならないよう、値が変わるときだけ DOM を更新します。

Android 固有

Android のカラムには Tauri IPC が無く、report_new_posts_count のような invoke は何も起きません。必要な機能はブリッジ経由で別実装します。MainActivity.kt のシグネチャを変えたら ProGuard の keep ルールも更新が必要です（android-notes.md）。
