Multi Column X とは

TweetDeck スタイルの Twitter/X クライアントです。複数アカウント・複数カラム（ホーム、通知、検索、リスト、カスタム URL、投稿専用、外部 URL）を 1 画面に並べて表示します。X の画面そのものは x.com を WebView で直接表示し、その上に NG ワード・広告非表示・自動更新などの加工をスクリプト注入で加える、というのが基本の作りです。

対応プラットフォーム

  • デスクトップ: Windows / Linux（配布は Windows インストーラ・Linux AppImage・deb。コード上は #[cfg(desktop)]）
  • Android: APK（#[cfg(mobile)] / target_os = "android"）

押さえる前提

Tauri では、アプリの画面は OS の WebView（ブラウザ部品）に HTML/JS で描かれ、ネイティブ処理は Rust が担当します。両者は invoke （呼び出し）と emit （通知）でやり取りします。

全体アーキテクチャ

まず「WebView が複数ある」ことを理解するのが近道です。メイン UI 用の WebView が 1 つ、その上（または横）に、カラムごとの x.com 用 WebView が並びます。箱をクリックすると詳細が開きます。

メインウィンドウ（1 つの WebView）
⇅
Rust バックエンド（単一プロセス）
⇅
カラム WebView（カラム数ぶん）

デスクトップでは、カラム WebView は Rust が window.add_child() でメインウィンドウに貼り付ける子 WebViewです。Linux だけは親クリップが効かないため独立ウィンドウになります（ linux-column-spec.md）。

MainActivity（1 つの Activity）
⇅
Rust（同一プロセス内の共有ライブラリ）
⇅
メイン WebView（背面）
⇅
カラム WebView（ネイティブ）

Android では Tauri の add_child() が使えないため、カラムは Tauri の WebView ではなく Android ネイティブの WebViewです。Rust が JNI で MainActivity を呼び、React の WebView の上に重ねて表示します。ネイティブ WebView には Tauri IPC が無いので、inject から Rust への通信は JS ブリッジ → Kotlin → JNI という別経路になります。

desktop との主な差

カラムの生成主体（Rust の Tauri API か Kotlin のネイティブ API か）、inject の通信経路、アカウント追加の完了検出、コンポーズ（Android は X 公式アプリを Intent で起動）が異なります。同名コマンドでも #[cfg(desktop)] / #[cfg(mobile)] で実装が分かれるので、変更時は両方を確認してください。

構成上の重要な制約

  • 子 WebView は OS ネイティブ部品のため CSS の z-index が効きません。ダイアログ表示中はカラムを画面外へ退避します（ column-layout-notes.md）。
  • アカウントごとに data_directory（Android は Profile）を 分けて Cookie を混ぜません。
  • x.com に IPC を開放するのは column-webview capability の remote 設定で、対象ドメインは x.com / twitter.com 系に限定されています。

開発環境・ビルド・テスト

前提ツール

  • Node.js 22 以上、Rust / Cargo、Tauri の前提条件（Windows は WebView2 など）
  • Android を触る場合は Android Studio / SDK（Gradle は src-tauri/gen/android 内）
  • 初回は npm install

コマンド早見表

コマンド 用途
npm run tauri:dev 開発起動（先に build:inject を実行）
npm run build:inject inject スクリプトのみビルド
npm run tauri:build / tauri:build:debug リリース / デバッグビルド
npm run tauri:android:build Android ビルド
npm run format TS / Rust / Kotlin の整形
npm run typecheck / npm run lint 型チェック / ESLint（lint:fix で自動修正）
npm run lint:rust clippy（警告もエラー）
npm run docs:build ユーザーガイド（VitePress）のビルド。リンク切れ検出を兼ねる
cargo test の前提

cargo test --manifest-path src-tauri/Cargo.toml の前に npm run build:inject が必要です（Rust が inject の *.js を include_str! で取り込むため）。inject の *.js は成果物で gitignore 対象、直接編集は禁止です。

テスト体系

契約テストが守っているもの

このプロジェクトには「2 か所以上に同じ事実を書かざるを得ない」箇所が多く、食い違いは実行時まで気づきにくい（特にリリースビルドや Android）ため、機械的に検査しています。

守っているもの 検査するテスト
コマンドの ACL（build.rs・capability・実装）の漏れ src-tauri/src/acl_contract.rs
IPC 名・イベント名の Rust/TS 一致 src/constants/ipc.contract.test.ts
設定既定値の Rust / TS / fixture の一致 src/types/defaults.contract.test.ts
SCSS 寸法と rem 定数の一致 src/lib/gridLayout.contract.test.ts
配色のコントラストsrc/lib/themeContrast.contract.test.ts
Android スワイプバーの色同期src/lib/swipeBarColors.contract.test.ts
辞書の ja/en キー集合src/i18n/resources.contract.test.ts
辞書の未使用キーsrc/i18n/unusedKeys.contract.test.ts
開発者向けログ・panic が英語であること src-tauri/src/log_language_contract.rs

契約テストが赤くなったら「どれかの定義だけを直した」サインです。メッセージに従い、対になる箇所も同時に更新します。

開発の進め方

詳細は CLAUDE.md と .claude/skills/ にあります。要点だけ示します。

  • ブランチ: develop を最新化 → develop から作業ブランチ → 作業完了後 push → develop への PR。新規ブランチ作成前にユーザー確認。
  • 1 度に 1 つのことを行い、作業ごとにコミット。必ずテストを書く。
  • 仕様はGherkin（docs/specs/<機能名>.feature、日本語）で承認を得る（機能追加・挙動変更・バグ修正）。→ .claude/skills/gherkin-spec/SKILL.md
  • TDD（t-wada 流）。Gherkin 由来のテストは実装後作成も可だが、ミューテーション確認は必須。→ .claude/skills/tdd/SKILL.md
  • 全体フロー（要求明確化 → プラン → 実装 → プロパティテスト → 完了処理）→ .claude/skills/feature-development-flow/SKILL.md
  • 完了時はフォーマッターとテストをオールグリーンにする。テスト名は日本語、Rust のテスト関数名に ASCII 大文字を使わない。
  • UI の寸法は rem、画面文言は辞書（i18n）に置く（日本語の直書きは ESLint でエラー）。
