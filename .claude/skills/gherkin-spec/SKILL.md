# Gherkin仕様定義（フェーズ1.5）

フェーズ1（`clarify-requirements`）で確定した要求を、Gherkin記法の**実行可能な粒度の仕様**にする。以降のプラン・テスト・手動テスト項目はすべてこの仕様を起点に導出する。

## 適用範囲

| 種別                               | 対象 | 備考                                                             |
| ---------------------------------- | ---- | ---------------------------------------------------------------- |
| 機能追加・挙動変更                 | 必須 | 新規 `.feature` または既存 `.feature` へのシナリオ追加・修正     |
| バグ修正                           | 必須 | 「再現シナリオ」（バグが起きる条件と本来の期待結果）を追加する   |
| 挙動不変のリファクタ / docs / CI設定のみ | 対象外 | 既存テストが仕様の代わり。対象外とした理由をユーザーに一言伝える |

## 進め方

1. **既存仕様の確認**: `docs/specs/` に対象機能の `.feature` があれば読み、追記・修正の形で扱う（重複ファイルを作らない）。
2. **シナリオ起案**: 確定要求から Feature / Scenario を起案する。正常系だけでなく、フェーズ1で挙がった異常系・境界・desktop/mobile差異も網羅する。
3. **テストレベルのタグ付け**: 各シナリオに自動化レベルのタグを付ける（下記）。
4. **ユーザー承認**: `.feature` の内容を提示し、**明示的な承認**を得る（CLAUDE.md「作業手順」）。承認前にプラン策定・実装へ進まない。
5. 承認後、コミットする（作業毎にコミット）。

## ファイル仕様

- 配置: `docs/specs/<機能名>.feature`（git管理。機能名は kebab-case、例: `column-reorder.feature`）
- 1ファイル1 Feature。関連するシナリオを `Background` / `Scenario Outline` で整理する
- 言語: 日本語Gherkin。先頭に `# language: ja` を書き、キーワードは `機能` / `背景` / `シナリオ` / `シナリオアウトライン` / `前提` / `もし` / `ならば` / `かつ` / `例` を使う
- Given/When/Then は**ユーザーから観測できる振る舞い**で書く。内部関数名・IPCコマンド名・DOMセレクタなど実装詳細は書かない
- 1シナリオ = 1つの振る舞い。When は原則1つ
- シナリオ名は「〜のとき〜になる」のようにテスト名にそのまま使える日本語の文にする（後段でテスト名になる）

## タグ（自動化レベル）

| タグ           | 意味                                                                             | 後段の扱い                                                    |
| -------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `@unit`        | 純粋関数・hook・単一モジュールで検証できる                                       | vitest / cargo test / Kotlin 単体テストを作成                 |
| `@integration` | 複数モジュール連携（コンポーネント間、フロント↔IPCモック、Storybook play等）で検証できる | 結合テスト（Storybook play function / モジュール結合テスト）を作成 |
| `@manual`      | 実機・実WebView・実OS・実X DOM・リリースビルド等に依存し自動化できない           | フェーズ6で手動テスト項目として出力                           |

- 1シナリオに複数タグを付けてよい（例: ロジックは `@unit`、実機での見え方は別シナリオで `@manual`）。
- `@manual` を付けたシナリオには、直前に `# 自動化不可: <理由>` のコメントを必ず書く。
- プラットフォーム限定は `@desktop` / `@mobile` / `@android` / `@linux` を併記する。

## 記述例

```gherkin
# language: ja
機能: カラムの並び替え

  背景:
    前提 カラムA, B, C がこの順で表示されている

  @unit
  シナリオ: 先頭カラムを右に移動すると2番目になる
    もし カラムAを右に1つ移動する
    ならば カラムの順序は B, A, C になる

  @unit
  シナリオ: 末尾カラムをさらに右に移動しても順序は変わらない
    もし カラムCを右に1つ移動する
    ならば カラムの順序は A, B, C のままである

  @manual @desktop @linux
  # 自動化不可: 実WebViewの子ウィンドウ配置はOSネイティブで、CIでは検証できない
  シナリオ: 並び替え後にカラムWebViewが正しい位置に表示される
    もし カラムAを右に1つ移動する
    ならば 各カラムの表示位置が並び順どおりになり、はみ出し表示がない
```

## 完了条件

- 対象の `.feature` がコミットされ、ユーザーが明示的に承認している
- すべてのシナリオに `@unit` / `@integration` / `@manual` のいずれかが付いている
- `@manual` シナリオすべてに自動化不可の理由コメントがある
- バグ修正の場合、再現シナリオが含まれている

承認されたらフェーズ2（`implementation-planning`）へ進む。

## 禁止事項

- ユーザー承認なしにプラン策定・実装へ進むこと
- 自動化できるシナリオを安易に `@manual` にすること（まず `@unit` / `@integration` を検討する）
- 実装詳細（関数名・IPCコマンド名・セレクタ）をGiven/When/Thenに書くこと
- Cucumber等のランナー導入を前提にすること（このプロジェクトでは既存のvitest / cargo test / Kotlinテストで実装する）
- `.feature` への参照（パス・ID・シナリオ対応表）をテストコード・コード内コメント・コミットメッセージに書くこと
