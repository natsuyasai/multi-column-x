# Gherkin仕様定義と仕様の確定（フェーズ1.5〜1.7）

フェーズ1.2〜1.3（`ears-requirements`）で作りギャップ分析した EARS 要求仕様を、Gherkin記法の**実行可能な粒度の仕様**にする。以降のプラン・テスト・手動テスト項目はすべてこの仕様を起点に導出する。

## 適用範囲

バグ修正では `bug-fix-flow` から本スキルの「ファイル仕様」「タグ」「記述例」を使う。EARS と「仕様の確定（フェーズ1.7）」の代わりに、不具合メモと `bug-fix-flow` の確定手順を使う。

| 種別                                     | 対象   | 備考                                                             |
| ---------------------------------------- | ------ | ---------------------------------------------------------------- |
| 機能追加・挙動変更                       | 必須   | 新規 `.feature` または既存 `.feature` へのシナリオ追加・修正     |
| バグ修正                                 | 必須   | 「再現シナリオ」（バグが起きる条件と本来の期待結果）を追加する   |
| 挙動不変のリファクタ / docs / CI設定のみ | 対象外 | 既存テストが仕様の代わり。対象外とした理由をユーザーに一言伝える |

## 進め方

1. **既存仕様の確認**: `docs/specs/` に対象機能の `.feature` があれば読み、追記・修正の形で扱う（重複ファイルを作らない）。`docs/specs/` は git 管理外のため、既存ファイルはメインチェックアウトにしか無い（新規 worktree には無い）点に注意する。
2. **シナリオ起案**: EARS 要求仕様から Feature / Scenario を起案する。すべての要求に対応するシナリオがあることを確認し、異常系・境界・desktop/mobile差異も網羅する。
3. **テストレベルのタグ付け**: 各シナリオに自動化レベルのタグを付ける（下記）。
4. **仕様の確定**: 下記「仕様の確定（フェーズ1.7）」を行う。確定前に実装指示書の作成・実装へ進まない。
5. 確定後も `.feature` は**コミットしない**（`git add docs/specs` もしない）。恒久的に残すべき設計判断（しきい値・実DOM知見・不採用案の理由など）は、`docs/development/` の該当ノート（ADR）に書いてコミットする。

## 仕様の確定（フェーズ1.7）

EARS（`.ears.md`）と Gherkin（`.feature`）を**まとめて1回で**確定する。方法はセッション最初に確認した承認モード（`tmp/plans/<日付>-<対象名>/session.md`）に従う。

どちらのモードでも、2ファイルは `SendUserFile` で会話に添付する（Remote Control の端末からは作業フォルダのファイルを開けないため）。`SendUserFile` が使えない場合は本文をチャットに出力する。

### 承認ありモード

添付したうえで、**明示的な承認**を得る。修正を求められたら直して、再度添付して承認を得る。

### 自律検証モード

検証用のサブエージェントを立てる（ギャップ分析とは別のエージェント。モデルはメインが都度判断。コードは変更させない）。渡すものは、ユーザーの元の依頼（原文）と質問への回答、`.ears.md`、`.feature`、`gap-analysis.md`。確認させる観点:

- 元の依頼と回答の内容が、要求に漏れなく反映されている。依頼に無い要求が増えていない
- すべての要求にシナリオがあり、すべてのシナリオが要求に対応する
- 期待結果が第三者に判定できる。要求間・シナリオ間に矛盾が無い
- ギャップ分析の重大な指摘が解消されている

指摘は「重大 / 軽微」で報告させる。重大な指摘は直して再検証する。**修正と再検証は2回まで**。2回で解消しない場合や、利用者に見える振る舞いの判断が要る場合は、止まってユーザーに聞く。重大な指摘が無くなったら確定し、仕様2ファイルを添付して（返事は待たずに）次へ進む。

以降の文書で「承認済み（確定した）仕様」は、承認ありモードではユーザーが承認した仕様、自律検証モードではこの検証を通った仕様を指す。

## ファイル仕様

- 配置: `docs/specs/<機能名>.feature`（`.gitignore` 対象。1対応ごとの一時記録として扱う。機能名は kebab-case、例: `column-reorder.feature`）
- 1ファイル1 Feature。関連するシナリオを `Background` / `Scenario Outline` で整理する
- 言語: 日本語Gherkin。先頭に `# language: ja` を書き、キーワードは `機能` / `背景` / `シナリオ` / `シナリオアウトライン` / `前提` / `もし` / `ならば` / `かつ` / `例` を使う
- Given/When/Then は**ユーザーから観測できる振る舞い**で書く。内部関数名・IPCコマンド名・DOMセレクタなど実装詳細は書かない
- 1シナリオ = 1つの振る舞い。When は原則1つ
- シナリオ名は「〜のとき〜になる」のようにテスト名にそのまま使える日本語の文にする（後段でテスト名になる）

## タグ（自動化レベル）

| タグ           | 意味                                                                                     | 後段の扱い                                                         |
| -------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `@unit`        | 純粋関数・hook・単一モジュールで検証できる                                               | vitest / cargo test / Kotlin 単体テストを作成                      |
| `@integration` | 複数モジュール連携（コンポーネント間、フロント↔IPCモック、Storybook play等）で検証できる | 結合テスト（Storybook play function / モジュール結合テスト）を作成 |
| `@manual`      | 実機・実WebView・実OS・実X DOM・リリースビルド等に依存し自動化できない                   | フェーズ6で手動テスト項目として出力                                |

- 1シナリオに複数タグを付けてよい（例: ロジックは `@unit`、実機での見え方は別シナリオで `@manual`）。
- `@manual` を付けたシナリオには、直前に `# 自動化不可: <理由>` のコメントを必ず書く。
- プラットフォーム限定は `@desktop` / `@mobile` / `@android` / `@linux` を併記する。

## 記述例

```gherkin
# language: ja
機能: カラムの並び替え

  背景:
    前提 カラムA, B, C がこの順で表示されている

  @unit
  シナリオ: 先頭カラムを右に移動すると2番目になる
    もし カラムAを右に1つ移動する
    ならば カラムの順序は B, A, C になる

  @unit
  シナリオ: 末尾カラムをさらに右に移動しても順序は変わらない
    もし カラムCを右に1つ移動する
    ならば カラムの順序は A, B, C のままである

  @manual @desktop @linux
  # 自動化不可: 実WebViewの子ウィンドウ配置はOSネイティブで、CIでは検証できない
  シナリオ: 並び替え後にカラムWebViewが正しい位置に表示される
    もし カラムAを右に1つ移動する
    ならば 各カラムの表示位置が並び順どおりになり、はみ出し表示がない
```

## 完了条件

- 対象の `.ears.md` と `.feature` が `docs/specs/` にあり、承認モードに従って確定している（コミットはしない）
- すべてのシナリオに `@unit` / `@integration` / `@manual` のいずれかが付いている
- `@manual` シナリオすべてに自動化不可の理由コメントがある
- バグ修正の場合、再現シナリオが含まれている

確定したらフェーズ2（`implementation-planning`）へ進む。

承認済みシナリオから導出する `@unit` / `@integration` テストは、TDD（Red先行）でも実装後の作成でもよい（`tdd` スキル「進め方の選択」参照）。選択はフェーズ2のプランに明記する。

## 禁止事項

- 確定していない仕様で実装指示書の作成・実装へ進むこと
- 承認ありモードなのに自律検証で代替すること
- 自動化できるシナリオを安易に `@manual` にすること（まず `@unit` / `@integration` を検討する）
- 実装詳細（関数名・IPCコマンド名・セレクタ）をGiven/When/Thenに書くこと
- Cucumber等のランナー導入を前提にすること（このプロジェクトでは既存のvitest / cargo test / Kotlinテストで実装する）
- `.feature` への参照（パス・ID・シナリオ対応表）をテストコード・コード内コメント・コミットメッセージに書くこと
- `.feature` をコミットすること（恒久化が必要な内容は `docs/development/` のノートへ）
