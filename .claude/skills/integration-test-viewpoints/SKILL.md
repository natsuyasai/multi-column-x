# 結合テスト観点出力

`check-creation`（format/typecheck/lint/test/build）では検出できない、ブラウザ・実機での手動確認観点を構造化して出力する。

## 使うタイミング

- 実装が完了し `check-creation` を通過した後、`superpowers:finishing-a-development-branch` でマージ/PR判断をする前
- レビュアーやテスターに確認観点を渡したいとき

## 入力

- `tmp/plans/<日付>-<対象名>/plan.md`（あれば）: 要求・完了基準・プラットフォーム影響を把握するため
- `git diff --stat` / `git diff`: 変更ファイル一覧と変更内容
- 変更対象のコンポーネント・モジュール構造（必要に応じて読み込み）

## 手順

1. `plan.md` があれば読み込み、要求・完了基準・プラットフォーム影響（desktop/mobile/Android）を確認する
2. `git diff --stat` で変更ファイル一覧を確認し、`git diff` で変更内容を把握する
3. 以下の観点で確認項目を洗い出す
   - 新規追加した機能の正常動作
   - 変更した既存機能の継続動作（回帰）
   - 入力バリデーション・エラーハンドリング（IPC呼び出し失敗、権限不足、通信エラー等）
   - 境界条件（空データ・大量データ・特殊文字・同時操作）
   - 画面遷移・ダイアログ表示/非表示（`hideColumnWebviews` / `recalculateAllBounds` が絡む変更は特に）
   - **desktop/mobile 両対応の機能は両プラットフォームの確認観点を含める**（`#[cfg(desktop)]` / `#[cfg(mobile)]` の分岐がある場合は必須）
   - Android の `MainActivity` メソッド変更を伴う場合は、リリースビルドでの動作確認（ProGuard keep ルール）を観点に含める
   - Linux 固有のクリッピング仕様（`linux_column_layout`）に触れる変更は、Linux環境での確認観点を明記する
4. 単体テスト・Storybook play function・プロパティテストで自動検証済みの内容は「自動テスト済み」と注記し、手動確認の優先度を下げる
5. 下記フォーマットで出力する

## 出力先

- `plan.md` と同じフォルダがあれば `tmp/plans/<日付>-<対象名>/integration-test.md` に出力する
- 該当フォルダがなければ出力先をユーザーに確認する（デフォルトはチャット上に直接出力）

## 出力フォーマット

| 項目     | 内容                                                             |
| -------- | ---------------------------------------------------------------- |
| No.      | 連番                                                             |
| カテゴリ | 正常系 / 異常系・バリデーション / エッジケース / 回帰 / UI・表示 |
| 観点     | 何を確認するか                                                   |
| 操作手順 | 具体的な操作ステップ                                             |
| 期待結果 | どうなれば正しいか                                               |
| 優先度   | 高 / 中 / 低                                                     |

## 注意事項

- 実際のIPC/WebView/inject連携が必要な確認（カラムWebViewの生成・再配置、ログイン検出、クラッシュ復旧等）を重点的に含める
- desktop/mobile/Android差異がある機能は、プラットフォームごとに行を分ける
- CI環境で確認できない観点（実機・実OS依存）はその旨を注記する

## 完了条件

- 変更内容に基づく確認観点の一覧が出力されている
- 自動テスト済みの項目には注記がある

出力後は `superpowers:finishing-a-development-branch` でマージ/PRの判断に進む。

## 禁止事項

- 単体テスト・Storybookで既にカバー済みの内容を「未確認」として重複記載すること
- プラットフォーム差異がある変更で、片方のプラットフォームの観点を省略すること
