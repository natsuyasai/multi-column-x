# アプリ開発フロー

このプロジェクトでのアプリ開発は、必ず以下のフェーズ順で進める。各フェーズには専用スキルがあり、メインエージェントが全体を管理しながら進行させる。

**原則: 前のフェーズが完了するまで次のフェーズに進まない。** 人が目を通すのは、最低限 EARS 要求仕様と Gherkin 仕様だけ。それ以外の成果物（ギャップ分析・実装指示書・進捗）はエージェント向けで、人の確認を求めない。

## フェーズ0: 承認モードの確認（セッション最初）

機能追加・挙動変更・バグ修正を始めるとき、**最初に** `AskUserQuestion` で承認モードを確認し、以降はその方針に従う（途中で変えるのはユーザーが指示したときだけ）。

| モード   | EARS・Gherkin の確定   | ブランチ・PR                                                                                        |
| -------- | ---------------------- | --------------------------------------------------------------------------------------------------- |
| 承認あり | ユーザーが承認する     | ブランチを作る前（フェーズ3）と PR を作る前（フェーズ7）にその都度確認する                          |
| 自律検証 | サブエージェントが検証 | **この時点で**ブランチ戦略（新規ブランチ名 / 既存ブランチ）と PR を作成するかを確認し、後は聞かない |

どちらのモードでも次はユーザーに聞く: 要求の明確化、利用者に見える振る舞いの判断、自律検証で解消できない指摘、X への外部影響・データ削除などの安全に関わる操作。PR のマージはどちらのモードでも自動で行わない。

確認結果は、対象名が決まった時点で `tmp/plans/<日付>-<対象名>/session.md` に記録する（モード、ブランチ戦略、PR作成の要否）。再開したセッションや委譲先はこれに従う。

挙動不変のリファクタ・docs・CI設定のみの変更は仕様を作らないため、フェーズ0〜1.7の仕様関連は対象外（ブランチは CLAUDE.md に従って確認する）。

## 各フェーズと使用スキル

| フェーズ                      | 内容                                                                                  | 使用スキル                    |
| ----------------------------- | ------------------------------------------------------------------------------------- | ----------------------------- |
| 0. 承認モード確認             | 上記                                                                                  | 本スキル                      |
| 1. 要求明確化                 | 要求の曖昧さ・不足を質問で潰し、合意した要求を確定する                                | `clarify-requirements`        |
| 1.2 EARS要求仕様              | `docs/specs/<機能名>.ears.md` を作成する                                              | `ears-requirements`           |
| 1.3 ギャップ分析              | サブエージェントが現状コードとの差と要求の抜けを分析する                              | `ears-requirements`           |
| 1.5 Gherkin仕様               | `docs/specs/<機能名>.feature` を作成し、`@unit` / `@integration` / `@manual` を付ける | `gherkin-spec`                |
| 1.7 仕様の確定                | EARS と Gherkin をまとめて、ユーザー承認または自律検証で確定する                      | `gherkin-spec`                |
| 2. 実装指示書                 | 作業するエージェント向けの指示書を `tmp/plans/` に作る（人のレビューなし）            | `implementation-planning`     |
| 3. 実装                       | 作業ブランチで、実装をサブエージェントに委譲し、作業毎にコミットする                  | `subagent-tdd-implementation` |
| 4. プロパティベーステスト     | 性質が明確で検証可能な場合だけ作成する                                                | `property-based-testing`      |
| 5. 完了処理                   | フォーマット・Lint・全テスト・ビルド                                                  | `check-creation`              |
| 6. 手動テスト項目出力（必須） | **対応内容と影響範囲だけ**の項目を `integration-test.md` に出力する                   | `integration-test-viewpoints` |
| 6.5 自律手動テスト            | エージェントが安全に実施できる項目を実施して結果を記録する                            | `autonomous-manual-test`      |
| 7. PR作成                     | 下記「PR作成」                                                                        | 本スキル                      |

## 仕様駆動ルール（必須）

- **機能追加・挙動変更・バグ修正では、EARS と Gherkin の仕様をフェーズ1.7で確定してから進む。** 仕様2ファイルはコミットしない。
- `.feature` のシナリオから、**単体テスト（`@unit`）と結合テスト（`@integration`）を作成する**（フェーズ3）。テスト名はシナリオ名を日本語で用い、仕様ファイルへの参照はテスト側に書かない。
- **Gherkinから導出するテストは、実装後に作成してもよい。** どちらで進めるかは実装指示書に明記する。実装後作成の場合も、シナリオごとのテスト作成とコミット前のミューテーション確認は必須（詳細は `tdd` スキル「進め方の選択」）。Gherkin対象外の変更・シナリオに無い追加テストはTDD。
- **自動化できないシナリオ（`@manual`）は手動テスト項目として必ず出力する**（フェーズ6）。
- **次回以降のリリースでも回帰確認が必要な観点は、`docs/release/pre-release-checklist.md` に項目として追加する**（フェーズ6で判断する）。チェックリストには項目の増減と内容の修正だけを書き、結果・実施日・実施回数は書かない。No. は各プレフィックスの最大番号の次を使い、再採番しない。
- 仕様が途中で変わったら、`.ears.md` と `.feature` を更新してフェーズ1.7をやり直す。
- バグ修正も当面はこのフローで進め、再現シナリオを含める。

## PR作成（フェーズ7）

承認ありモードでは作成してよいかを確認する。自律検証モードでは `session.md` のとおりにする（作成しない指定なら push もせず、報告して終える）。

1. 未コミットの変更が無いことを確認する。develop / main 上なら中止する
2. `git fetch origin develop` の後、`git merge-base --is-ancestor origin/develop HEAD` で最新の develop を含むことを確認する。含まなければ develop を取り込んで、フェーズ5をやり直す
3. `git push -u origin HEAD`（`--force` と `--no-verify` は使わない）
4. `gh pr list --head <branch>` で既存の PR を確認し、あれば使う
5. `.github/pull_request_template.md` の書式で `gh pr create --base develop`。確認事項は実際に行ったものだけにチェックし、手動テストの結果（OK / 未実施とその理由）を書く。リポジトリは公開なので、秘匿情報・個人情報・ローカル環境の情報（パス、ユーザー名、端末名など）を書かない
6. PR の URL を報告する

## 横断ルール（全フェーズ共通）

- **ブランチ運用**: 最新化した `develop` から作業ブランチを切り、PR は **`develop` 宛て**に作成する（`main` へは `version-release` でのみ反映する）。
- **PR 本文**: `## リリースノート` にユーザー向けの変更点を箇条書きする（カテゴリは PR タイトル接頭辞 `feat:` / `fix:` / その他）。内部的な変更のみの PR はセクションを空にする。
- **同様のミスの指摘が複数回発生したら、必ず `CLAUDE.md` に再発防止ルールを追記する。** → `record-recurring-mistakes`
- セキュリティに関わる変更（WebView/IPC/inject/capabilities/外部入力）では `security-review` を併用する。
- **各フェーズの手順は途中で打ち切らず、順番通り最後まで実行する。**
  - 途中で作業を止めて「次に何をしますか」と尋ねない。
  - スキップしてよいのはユーザーが明示的に指示したときだけ。
  - ユーザーに確認するのは、フェーズ0とスキルが定める箇所だけ。独自の確認を差し込まない。
  - check-creation でエラーが出た場合は、修正してから続きを実行する。

## このプロジェクト特有の留意点

- **desktop / mobile**: 同名コマンドでも `#[cfg(desktop)]` / `#[cfg(mobile)]` で実装が異なる。両方確認する。
- **inject スクリプト**: `src-tauri/src/inject/_src/` を変更したら `npm run build:inject`。ビルド済み `.js` は編集禁止。inject の開発手順は `inject-script-dev` スキルに従う。
- **Tauri コマンドの追加・削除**: `src-tauri/build.rs` の `AppManifest` と capability（`default.json` / `column-webview.json`）の更新が必須（`acl_contract.rs` の契約テストで検出される）。
- **領域別の設計ノート**: 変更対象に対応する `docs/development/*-notes.md`（CLAUDE.md「アーキテクチャ上の重要な制約」が参照先を示す）を着手前に読む。
- **UI の変更**: React / SCSS を変更する場合は `ui-design-principles` スキル（余白・文字サイズ・状態・a11y・Android の 44px）を参照する。
- **serde 命名**: JS側 camelCase には `#[serde(rename)]` が必須。
- **Android**: `MainActivity.kt` のメソッド変更時は ProGuard keep ルールを同期（リリースビルドで動作確認）。

## メインエージェントの責務

- 各フェーズの完了判定とフェーズ間のゲート管理
- フェーズ0の承認モードに従った仕様の確定と、要求↔シナリオ↔テスト/手動項目の漏れチェック
- フェーズ3では**実装そのものをサブエージェント（知的作業は `model: sonnet`、機械的な作業は `model: haiku`）に委譲**し、自身はレビュー・進行管理・コミット・品質チェック実行・ドキュメント整備に徹する
- 横断ルールの監視（同じ指摘の再発をCLAUDE.mdに反映）

## 禁止事項

- 承認モードを確認せずに仕様の作成・確定を進めること
- 要求が曖昧なまま仕様を作ること
- 仕様が確定していないまま（対象外の変更を除き）実装指示書の作成や実装に進むこと
- `@unit` / `@integration` シナリオにテストがない、または `@manual` シナリオが手動テスト項目に出力されていない状態で「完了」と報告すること
- 作業ブランチを切らずに（develop / main で）実装を進めること
- PR を `main` 宛てに作成すること（`version-release` を除く）、PR を自動でマージすること
- メインエージェントが自分で実装を書き進めてしまうこと（委譲が原則）
- TDDのRed-Green-Refactorを飛ばすこと（ただしGherkinから導出するテストを「実装後作成」で進める場合を除く）
- 完了処理（format/lint/test/build）を省略して「完了」と報告すること
- フェーズ6（手動テスト項目出力）を省略すること
