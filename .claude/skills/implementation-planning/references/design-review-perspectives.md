# 設計フェーズ検討観点

実装プラン策定時に、以下の観点について本タスクでの該当性と対応方針を検討する。

**対象**: 変更範囲が複数ファイル・複数モジュールにまたがる、または非自明な設計判断を伴うタスク。
小さな修正（1ファイルの軽微な変更、CSSのみの調整等）では全観点を精査する必要はなく、明らかに非該当な観点は省略してよい。

> **定型チェックとの棲み分け**: format / typecheck / lint / test / build の正常終了は `check-creation`（フェーズ5）で常に実施される。ここで検討するのは、それら定型チェックだけでは判定できない**タスク固有の設計判断・完了判定**である。

該当する観点は実装プランの該当セクションに反映する:

- 完了基準に関する観点（1-1〜1-5） → 「完了基準と検証方法」セクション
- 設計品質に関する観点（2-1〜2-11） → 「対応方針」セクション

該当しない観点は「該当なし」と明記する（検討した事実を残す）。ユーザーへのプラン確認時に、検討結果の妥当性についてもレビューを依頼する。

---

## 1. 完了基準に関する観点

### 1-1. 対象機能の自動テスト

- 単体テスト（vitest / `cargo test` / `:app:testUniversalDebugUnitTest`）でカバーすべき関数・モジュールのスコープ
- Storybook Story / play function が必要か（UIコンポーネントの見た目・操作）
- どのテストがGREENであれば「実装完了」とみなすかを定義する

### 1-2. リグレッションテスト

- 今回の変更が既存機能に影響しうる範囲を特定する
- 既存テストが変更対象の振る舞いを十分カバーしているか確認する
- 不足していれば、実装**前に**追加すべきテストを決める

### 1-3. テストカバレッジの範囲

- 正常系（必須）/ 境界値（推奨）/ エラー系（該当時必須）
- 入力パターンが広い純粋関数は `property-based-testing`（フェーズ4）適用を検討する
- desktop/mobile で分岐するロジックは両方の分岐をカバーする

### 1-4. UIテスト・ビジュアルテストの網羅度

- 新規/変更UIコンポーネントの状態バリエーション（初期表示・ローディング・空データ・エラー）
- 新規コンポーネントは最低限デフォルト + 主要バリエーション2〜3パターンをStoryで用意する
- ライト/ダークテーマ切り替え（`data-theme`）が絡む場合は両テーマを確認する

### 1-5. 手動確認が必要な範囲

- 自動テストではカバーできない項目（実機・実OS依存、WebView/IPC連携の実挙動等）を洗い出す
- 洗い出した項目は `integration-test-viewpoints` スキルの出力に反映する前提で記録する
- 自動化可能なものは可能な限りテストに落とし込む

## 2. 設計品質に関する観点

### 2-1. 影響範囲の特定と副作用リスク

- 変更対象が共通関数・共通コンポーネント・共有フック（`src/lib/` 等）に含まれるか
- 変更対象を参照している箇所の一覧
- 型変更・インターフェース変更が利用箇所に与える影響
- desktop/mobile 両方の実装（`#[cfg(desktop)]` / `#[cfg(mobile)]`）に影響するか

### 2-2. パフォーマンスへの考慮

- 大量データ処理・描画、重い計算処理の有無
- 不要な再計算・再レンダリングの発生リスク（React の依存配列・memo化）
- 高頻度イベント（スクロール等）への対応要否（`src/lib/rafThrottle.ts` のような間引きが必要か）
- 該当しない場合は「パフォーマンス観点: 該当なし」と明記する

### 2-3. エラーハンドリング・異常系の設計

- Tauri IPC呼び出し失敗時: ユーザーへの表示内容・リトライの有無・状態の巻き戻し
- WebView/WebProcessクラッシュ時の復旧方針（該当する場合は既存の自動復旧の仕組みとの整合性）
- バリデーションエラー: 表示方法とタイミング
- 各異常系について「何が起きたら」「何を表示し」「状態をどうするか」を定義する

### 2-4. アクセシビリティ要件

- フォーカス管理: ダイアログ表示時のフォーカストラップ・閉じた後のフォーカス復帰
- キーボード操作: Tab / Enter / Escape で期待通り操作できるか
- `aria-label` 等の付与（`component-create` スキルのa11yチェックリストに準拠）
- 新規コンポーネントではa11y警告を残さない（既存コード由来の警告は段階解消のためwarn許容）

### 2-5. 既存データ・状態との整合性

- zustandストアに新しいプロパティを追加する場合、既存の参照箇所への影響
- 型の変更（プロパティ追加・削除・型変更）がある場合のマイグレーション
- 永続化データ（設定ファイル・ローカルストレージ等）が新しい型に適合するか

### 2-6. 権限パターンの確認

- 対象機能に権限制御・アカウント種別による出し分けが必要か
- 必要な場合、パターンごとの期待する振る舞いを表形式で整理する
- 該当しない場合は「権限パターン: 該当なし」と明記する

### 2-7. ローディング表示の設計

- 非同期処理中（IPC呼び出し・WebView生成等）のローディング表示の要否と粒度
- ローディング中のユーザー操作の制御（ボタン無効化等）
- 該当しない場合は「ローディング表示: 該当なし」と明記する

### 2-8. 編集画面の情報破棄（離脱防止）

- 未保存の変更がある状態でダイアログを閉じる・画面遷移する際の確認要否
- 「未保存の変更がある」状態の判定方法
- 該当しない場合（参照のみの画面等）は「情報破棄: 該当なし」と明記する

### 2-9. バリデーションの設計

- 入力のバリデーションタイミング（入力中 / フォーカスアウト時 / 送信時）とルール定義場所
- エラーメッセージの表示方法
- 該当しない場合は「バリデーション: 該当なし」と明記する

### 2-10. Tauri IPC / API呼び出しの設計

- 呼び出しタイミング（画面表示時 / ユーザー操作時 / ポーリング）
- 重複呼び出しの排除（デバウンス・スロットル）要否
- serde のフィールド命名（JS側camelCaseには `#[serde(rename)]` が必要）に影響するか
- 該当しない場合は「IPC呼び出し設計: 該当なし」と明記する

### 2-11. 状態管理の設計方針

- 新たに管理が必要な状態の洗い出しと配置先判断:
  - コンポーネントローカル（`useState`）: そのコンポーネント内でしか使わない状態
  - 共有フック（`src/hooks/` 等）: 複数箇所で共有するがグローバルである必要がない状態
  - zustandストア: アプリケーション全体・複数カラム間で共有が必要な状態
- 既存の同種状態の管理パターンとの一貫性を確認する
- 該当しない場合は「状態管理設計: 該当なし」と明記する
