# バグ修正フロー

**本来の動作が決まっていて、実際の動きがそれと違う**場合はこのフローで進める。期待する動作を新しく決める・変える場合や、調査の途中で仕様・設計の変更が必要と分かった場合は、理由を伝えて通常フロー（`feature-development-flow`）に切り替える。

承認モードの扱い、ブランチ運用、PR作成、横断ルールは `feature-development-flow` と同じ。ここでは違いだけを定める。

## 手順

| 順                      | 内容                                                                  | 使用スキル                    |
| ----------------------- | --------------------------------------------------------------------- | ----------------------------- |
| 0. 承認モード確認       | `feature-development-flow` のフェーズ0                                | `feature-development-flow`    |
| 1. 不具合の確認         | 現象・再現手順・期待動作・環境を確認し、不足があれば質問する          | 本スキル                      |
| 2. 再現と原因調査       | 下記                                                                  | 本スキル                      |
| 3. 横展開の洗い出し     | 同じ原因の箇所を CodeGraph と検索で洗い出す                           | 本スキル                      |
| 4. 不具合メモと Gherkin | 下記の2ファイルを作る。EARS とギャップ分析は作らない                  | 本スキル / `gherkin-spec`     |
| 5. 確定                 | 承認モードに従い、承認または自律検証                                  | 本スキル                      |
| 6. 実装指示書と実装     | 短い指示書を `tmp/plans/` に作り、サブエージェントに委譲する          | `subagent-tdd-implementation` |
| 7. 完了処理以降         | プロパティテスト（該当時）→ 品質チェック → 手動テスト → 自律実施 → PR | 通常フローのフェーズ4〜7      |

## 2. 再現と原因調査

**原因を確認するまで修正しない。** 症状を隠すだけの対処（例外の握りつぶし、待ち時間の追加など）を原因の修正の代わりにしない。

1. 再現する。できれば自動テストか実機で。`inject-script-dev` の実DOM確認の発動条件に該当する場合は、実 DOM を調べる
2. 事実を集める: エラー内容・ログ・直近の変更（`git log`）・呼び出し経路。該当する `docs/development/*-notes.md` を読み、過去に同じ症状が無いか確認する
3. 仮説を**1つずつ**立てて検証する。外れた仮説のための変更は戻してから次に進む
4. 原因を、根拠（`ファイル:行`、観測した値）とともに説明できる状態にする

調査用の一時ログや変更はコミットしない。

### 再現できない場合

| 状況                             | 扱い                                                                                     |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| コード上の根拠で原因を説明できる | 修正を進める。不具合メモと PR に「未再現」と書き、手動テスト項目に確認を残す             |
| 根拠を持って原因を説明できない   | 止まって、調べた内容と仮説を報告し、追加情報・ログ追加・推測での対処のどれにするかを聞く |

## 3. 横展開

- **同じ原因**の箇所は、不具合メモと再現シナリオに追記してまとめて直す
- **別の原因**の不具合は直さず、報告する

## 4. 不具合メモと再現 Gherkin

どちらも `docs/specs/` に置く（git 管理外。コミットしない。テストコード・コメント・コミットから参照しない）。リポジトリは公開なので、PR 本文にメモを写すときは秘匿情報・個人情報・ローカル環境の情報を除く。

- `docs/specs/<名前>.bug.md`（短く書く）

  ```markdown
  # <不具合名>

  ## 現象

  ## 再現手順

  （環境を含む。再現できていなければ「未再現」）

  ## 期待する動作

  ## 原因と根拠

  ## 直し方

  （影響を受ける機能と、同じ原因の箇所を含む）
  ```

- `docs/specs/<名前>.feature`: 再現シナリオ（不具合が起きる条件と本来の期待結果）。書き方・タグは `gherkin-spec` に従う

## 5. 確定

2ファイルを `SendUserFile` で添付する（使えない場合は本文を出力する）。

- **承認ありモード**: 原因と直し方について、明示的な承認を得る
- **自律検証モード**: 調査したエージェントとは別のサブエージェントに検証させる（モデルはメインが都度判断。コードは変更させない）。ユーザーの元の報告（原文）と2ファイルを渡し、次を確認させる
  - 原因の根拠がコード・観測値と合っていて、現象をすべて説明できる
  - 直し方が原因に対応していて、影響範囲と同じ原因の箇所に漏れが無い
  - 再現シナリオが、修正前は失敗し修正後に成功する内容になっている
  - 重大な指摘の修正と再検証は**2回まで**。解消しなければ止まって聞く

## 6. 実装

- 指示書（`tmp/plans/<日付>-<対象名>/plan.md`）はエージェント向けに短く書く: 原因、変更箇所、再現テスト、影響範囲、コミットのトレーラー。人のレビューは求めない
- ブランチは `fix/<対象名>`
- **再現テストを先に書き、Red（不具合と同じ理由の失敗）を確認してから直す。** 通常フローの「Gherkin由来のテストは実装後作成も可」はバグ修正では使わない。委譲プロンプトに明記する
- 自動テストにできない再現シナリオ（`@manual`）は、手動テスト項目にする
- **修正を3回試しても解消しない場合は止まる。** 原因の理解か設計が違う可能性を報告して聞く

## 7. 完了処理以降

- 手動テストは、直した不具合の再現手順と影響範囲だけに絞る（`integration-test-viewpoints`）
- PR タイトルは `fix:`。本文に原因と直し方を短く書き、`## リリースノート` にユーザー向けの修正内容を書く
- 同じ原因の不具合が繰り返されている場合は `record-recurring-mistakes` を使う

## 禁止事項

- 承認モードを確認せずに始めること
- 原因を確認する前に修正すること（「未再現」で根拠のある場合を除き、再現も省略しない）
- 再現テストの Red を確認せずに直すこと（自動化できないシナリオを除く）
- 別の原因の不具合や無関係なリファクタを同じ修正に混ぜること
- 仕様の変更が必要なのに、このフローのまま進めること
