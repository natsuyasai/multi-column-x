# EARS要求仕様とギャップ分析（フェーズ1.2〜1.3）

人が目を通すのは、この EARS 要求仕様と Gherkin 仕様（`gherkin-spec`）だけである。**この2つだけを読めば、何ができるようになるか・何をしないかが判断できる**内容にする。

適用範囲は `gherkin-spec` と同じ（機能追加・挙動変更・バグ修正。挙動不変のリファクタ・docs・CI設定のみの変更は対象外）。

## フェーズ1.2: EARS要求仕様の作成

### ファイル

- 配置: `docs/specs/<機能名>.ears.md`（`.gitignore` 対象。コミットしない。機能名は `.feature` と同じ kebab-case）
- `docs/specs/` は git 管理外のため、新規 worktree には存在しない

### 構成

```markdown
# <機能名> 要求仕様

## 背景・目的

（2〜3行）

## 要求

- REQ-1: …
- REQ-2: …

## 対象外

- …

## 前提・判断

- （エージェントが補った判断と理由。人が覆せるように書く）
```

### EARS の書き方

1要求 = 1文 = 1つの振る舞い。主語は「システム」か画面・機能の名前にする。

| パターン     | 書き方                                             | 使う場面     |
| ------------ | -------------------------------------------------- | ------------ |
| 常時         | システムは、〜する。                               | 常に成り立つ |
| イベント     | 〜したとき、システムは〜する。                     | 操作・出来事 |
| 状態         | 〜の間、システムは〜する。                         | 状態が続く間 |
| 望まない事象 | もし〜した場合、システムは〜する。                 | 異常・失敗   |
| 任意機能     | 〜が有効な場合（〜の環境では）、システムは〜する。 | 設定・OS差   |
| 複合         | 〜の間、〜したとき、システムは〜する。             | 上記の組合せ |

- ユーザーから観測できる振る舞いで書く。関数名・IPCコマンド名・DOMセレクタは書かない
- 「適切に」「必要に応じて」「など」「できるだけ」のような判定できない語を使わない。数値・条件を書く
- desktop / mobile / Android / Linux で挙動が違う場合は、環境ごとに要求を分ける
- 利用者に見える複数の実現案がある場合は、ここで決めて要求にする（実装指示書の段階に持ち越さない）

## フェーズ1.3: ギャップ分析（サブエージェント）

EARS を書き終えたら、**必ずサブエージェントを立てて**分析する。書いた本人（メイン）が自分で済ませない。

- モデルはメインが要求の規模と難度で都度判断する（CLAUDE.md「サブエージェント運用」の例外）。委譲前に「メイン=<モデル名> / サブエージェント=<モデル名>」を出力する
- コードは変更させない

委譲プロンプトに入れるもの:

- ユーザーの元の依頼（原文）と、フェーズ1で確認した回答
- EARS ファイルの絶対パス
- 次の2種類を分けて報告すること
  1. **現状コードとの差**: 要求ごとに「実装済み / 一部 / 未実装 / 現状と衝突」を根拠（ファイルパス:行）付きで示す。影響を受ける既存機能の一覧（手動テストの範囲の根拠になる）。コード調査は CodeGraph を先に使い、該当する `docs/development/*-notes.md` を読む
  2. **要求自体の抜け**: 異常系・境界・プラットフォーム差・既存データとの互換・曖昧な語・要求間の矛盾・元の依頼との不一致
- 各指摘に「重大（このまま作ると要求を満たさない・壊れる）/ 軽微」を付けること

## 指摘の扱い

| 指摘の種類                         | 扱い                                                      |
| ---------------------------------- | --------------------------------------------------------- |
| 利用者に見える振る舞いの判断が要る | どちらの承認モードでも `AskUserQuestion` でユーザーに聞く |
| コードや既存仕様から答えが決まる   | EARS を直し、補った判断は「前提・判断」に書く             |
| 内部実装だけの話                   | EARS に書かず、実装指示書（フェーズ2）に引き継ぐ          |

分析結果は `tmp/plans/<日付>-<対象名>/gap-analysis.md` に保存する（人向けに整形しなくてよい）。「影響を受ける既存機能」はフェーズ2と6で使う。

完了したらフェーズ1.5（`gherkin-spec`）へ進む。

## 禁止事項

- ギャップ分析を省略すること、メインが自分で代行すること
- 指摘のうち判断が要るものを推測で埋めること
- EARS に実装詳細を書くこと、`.ears.md` をコミットすること
- テストコード・コメント・コミットに `.ears.md` への参照や要求番号を書くこと
