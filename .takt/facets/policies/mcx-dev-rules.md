# Multi Column X 開発規約ポリシー

プロジェクト直下の `CLAUDE.md` の運用規約に従い、テスト・仕様・コード規約・品質ゲートを満たした状態でのみ完了とする。

## 原則

| 原則                                | 基準                                                                                |
| ----------------------------------- | ----------------------------------------------------------------------------------- |
| 日本語で書く                        | 回答、コミットメッセージ、テストケース名は日本語で書く                              |
| 仕様を先に確定する                  | 機能追加・挙動変更・バグ修正は Gherkin 仕様に沿う                                   |
| テストを必ず作る                    | 変更には対応するテストを作成する                                                    |
| 警告を残さない                      | エラーと警告は新規コードで残さず、すべて修正する                                    |
| 品質ゲートを実行して証拠にする      | 完了前にコマンドを実行し、終了結果を報告に含める                                    |
| 同期箇所を漏らさない                | 複数箇所の同期が必要な変更は、すべてを更新する（知識 `mcx-tauri` を参照）           |
| 最新の develop から派生して作業する | 作業前に develop を最新化し、そこから作業ブランチを作る。完了したら PR まで作成する |

## テスト規約

| 基準                                                                                                          | 判定                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| テストケース名が日本語でない                                                                                  | REJECT                                                                                                                                          |
| Rust のテスト関数名に ASCII 大文字を含む（例: `ngWordsは…`）                                                  | REJECT（`non_snake_case` 警告で `cargo clippy -- -D warnings` が落ちる。英単語を含める場合はすべて小文字にする。非 ASCII の日本語部分は対象外） |
| テストコード・コメント・コミットに `.feature` への参照を書く                                                  | REJECT                                                                                                                                          |
| 変更に対応するテストがない                                                                                    | REJECT                                                                                                                                          |
| Gherkin の対象外の変更（挙動不変のリファクタ、シナリオに無い追加テスト、プロパティテスト）を TDD で進めている | OK                                                                                                                                              |
| Gherkin の対象外の変更で、Red を確認せずにテストと実装を同時に書いている                                      | REJECT                                                                                                                                          |

## Gherkin 仕様

| 基準                                                                                                    | 判定                                                                                        |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 機能追加・挙動変更・バグ修正で、仕様（`docs/specs/<機能名>.feature`、日本語 Gherkin）が承認されていない | REJECT（ユーザー承認が必須。承認が取れない場合は報告して止まる）                            |
| `docs/specs/*.feature` をコミットする                                                                   | REJECT（コミットしない一時記録。永続化が必要な内容は ADR として `docs/development` へ置く） |
| 承認済みシナリオごとに対応する単体テスト（`@unit`）・結合テスト（`@integration`）がない                 | REJECT                                                                                      |
| Gherkin 由来のテストを実装後に作成する                                                                  | OK（Red 先行は必須でない）                                                                  |
| 実装後に作成したテストを、主要な条件分岐を一時的に壊して Red になることを確認せずにコミットする         | REJECT（ミューテーションでの検証は必須）                                                    |
| 自動化できないシナリオ（`@manual`）が手動テスト項目として出力されていない                               | REJECT                                                                                      |
| 挙動不変のリファクタ、docs、CI 設定のみの変更に Gherkin を要求する                                      | REJECT（対象外）                                                                            |

## TypeScript / フロントエンド規約

| 基準                                                                                | 判定                                           |
| ----------------------------------------------------------------------------------- | ---------------------------------------------- |
| import 順が 外部パッケージ → vitest / storybook → `@/`（internal）→ 相対パス でない | REJECT                                         |
| 同一グループ内がアルファベット昇順でない                                            | REJECT                                         |
| import のグループ間に空行を入れている（`newlines-between: "never"`）                | REJECT                                         |
| 新規コードが `@/*`（`src/*`）エイリアスを使わず深い相対パスで参照している           | REJECT                                         |
| 新規コードに ESLint 警告（a11y 含む）を残している                                   | REJECT                                         |
| Storybook の `<Name>.stories.tsx` をコンポーネントと別ディレクトリに置く            | REJECT（同じディレクトリにコロケーションする） |
| Storybook 用にバレル（`index.ts`）を作る                                            | REJECT                                         |
| `npm run lint:fix` で import 順を自動整列する                                       | OK                                             |

## inject スクリプトと TDD の要点

| 基準                                                                                                                | 判定                                                              |
| ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `src-tauri/src/inject/*.js`（生成物）を直接編集する                                                                 | REJECT（`_src` を編集して `npm run build:inject` で再ビルドする） |
| inject 変更後に `npm run build:inject` を実行していない                                                             | REJECT                                                            |
| inject のテストを `_src` の同ディレクトリにコロケーションしていない（`<name>.test.ts` / `<name>.property.test.ts`） | REJECT                                                            |
| inject の実 DOM 検証が必要な変更で、方針 `mcx-real-webview-investigation` を満たしていない                          | REJECT                                                            |
| TDD で進める場合に、テストを 1 件追加して Red を確認してから最小実装で Green にしている                             | OK                                                                |
| TDD で進める場合に、テストと実装を同時に書いて「Red」と報告している                                                 | REJECT                                                            |
| 1 つの関数の複数テストで、最初の Red を通す実装に完成形を書き、残りのテストを追加時点で Green にしている            | REJECT（実装は Red のテスト 1 件を通す最小限に留める）            |

## 品質ゲート

完了前に次のコマンドを実行し、すべて通すこと。コマンド gate では強制されないため、この方針が必須の確認手段になる。

| コマンド            | 実行条件            |
| ------------------- | ------------------- |
| `npm run typecheck` | 常に                |
| `npm run lint`      | 常に                |
| `npm test`          | 常に                |
| `npm run lint:rust` | Rust を変更した場合 |

| 基準                                                                                       | 判定   |
| ------------------------------------------------------------------------------------------ | ------ |
| 上記のコマンドを実行せずに完了を報告する                                                   | REJECT |
| 完了報告に、各コマンドの終了結果（成功・失敗）がない                                       | REJECT |
| 失敗や警告が残ったまま完了を報告する                                                       | REJECT |
| 失敗したコマンドを、実行結果の根拠なく「既存の問題」として扱う                             | REJECT |
| Rust を変更したのに `npm run lint:rust` を実行していない                                   | REJECT |
| inject を変更した場合に、`npm run build:inject` の後で Rust のテストやビルドを実行している | OK     |

## ブランチ・PR 運用

作業は、最新化した develop から派生したブランチで行い、完了したら develop 向けの PR を作成するところまでを一連で行う。

| 基準                                                                                                                        | 判定   |
| --------------------------------------------------------------------------------------------------------------------------- | ------ |
| develop を最新化（`git fetch` 後にリモートと一致を確認）せずに作業ブランチを作る                                            | REJECT |
| develop 以外のブランチ（他の作業ブランチ等）から派生して作業する                                                            | REJECT |
| develop や main に直接コミットする                                                                                          | REJECT |
| 作業ブランチが最新の develop から派生していることを確認していない（`git merge-base --is-ancestor origin/develop <branch>`） | REJECT |
| 作業が完了したのに push と PR 作成をしていない                                                                              | REJECT |
| PR のベースが develop でない                                                                                                | REJECT |
| PR 本文が `.github/pull_request_template.md` の書式（概要・リリースノート・確認事項）に沿っていない                         | REJECT |
| 作業ごとにコミットし、コミットメッセージを日本語で書いている                                                                | OK     |
